`middleware.CORS` enforces strict cross-origin semantics as plain HTTP middleware. There is no registry and no adapter: build an `Options` value in `main` (from the app's own YAML/env) and wire it outermost with `r.Use` before any `Handle` call.

Use it when browsers call the API from another origin. Non-browser clients are unaffected: requests without an `Origin` header pass through untouched.

## Config

CORS is the one middleware that takes options. The framework owns no `cors` config section; decode the app's own block straight into `middleware.Options` (snake_case `json`/`toml`/`yaml` tags):

```yaml
cors:
  allowed_origins: ["https://example.com"]
  allowed_methods: ["GET", "POST", "PUT", "PATCH", "DELETE"]
  allowed_headers: ["Content-Type", "Authorization"]
  exposed_headers: ["X-Request-Id"]
  allow_credentials: true
  max_age: 10m
```

Env mapping is app-level too: read vars such as `CORS_ALLOWED_ORIGINS` in `main`, split, and pass the resulting `Options` here. `MaxAge` stays `time.Duration` per repo convention and renders to delay-seconds on the wire (`10m` becomes `600`).

```go
handler := middleware.CORS(middleware.Options{
    AllowedOrigins:   []string{"https://example.com"},
    AllowedMethods:   []string{"GET", "POST", "PUT", "PATCH", "DELETE"},
    AllowedHeaders:   []string{"Content-Type", "Authorization"},
    ExposedHeaders:   []string{"X-Request-Id"},
    AllowCredentials: true,
    MaxAge:           10 * time.Minute,
})(mux)
```

## Behavior

| Request | Response |
|---|---|
| No `Origin` header (not a CORS request) | passthrough, no CORS headers |
| Allowed origin, simple request | handler runs; `Access-Control-Allow-Origin` echoes the origin, plus `Vary: Origin`, `Access-Control-Expose-Headers` when set, and `Access-Control-Allow-Credentials: true` when enabled |
| Allowed origin, preflight `OPTIONS` + `Access-Control-Request-Method` | method and requested headers validated: match answers `204` with `Allow-Origin`, `Allow-Methods`, `Allow-Headers` (echoes the request, else the configured join), `Max-Age` when positive, and full `Vary`; mismatch answers `403` with no `Allow-Origin` |
| Disallowed origin | never reflected: simple requests pass through without CORS headers, preflights fall through to the next handler |

## Validation

`Options.Validate` rejects fail-open shapes: empty origin or method lists, blank entries, wildcard origin (`*`) combined with `AllowCredentials`, and negative `MaxAge`. `CORS` with invalid options fails closed, responding `500 {"error":"internal error"}` instead of running open.

Wildcard without credentials echoes `*` for any origin. `DefaultCORSMaxAge` (`0`) disables the `Max-Age` header, forcing browsers to re-run preflight per request.

## Wire order

`CORS` goes outermost so preflights short-circuit before logging or rate limiting, and `r.Use` must run before any `Handle` call because the `stdhttp` driver snapshots middleware per route at registration. CORS is HTTP-only: there is no gRPC twin (gRPC has no preflight concept).

## Troubleshooting

1. **Preflights logged or rate-limited.** `CORS` is inside `RequestLogger`/`RateLimit`. Move it outermost.
2. **Browser blocks a valid origin.** The origin is not an exact allowlist match; disallowed origins get no CORS headers by design. Add the exact origin.
3. **Unexpected 403 on preflight.** The request method or a requested header is outside the allowlist. Header matching is case-insensitive; add the missing entry.
4. **500 on every CORS request.** `Options` is invalid (often `*` with credentials, or an empty list). Fix `Validate` and rewire.
5. **`Use` has no effect on stdhttp.** It was registered after the route. Move `r.Use(CORS(...))` above all `Handle` calls.
