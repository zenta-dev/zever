---
title: Versioning
description: One lockstep version across every Zever module, per-module tags, and replace-less consumption.
---

Zever ships ~180 Go modules (one per battery, adapter, helper, tool. 176 in the workspace plus two out-of-tree proofs) under one lockstep version. No umbrella module, no root `go.mod`: require only what you use, all pinned to the same version.

## One version, per-module tags

Each release tags every module as `<path>/vX.Y.Z` (e.g. `container/v0.8.0`, `adapters/db/sqlite/v0.8.0`) via `tools/tag-release.sh`. A bump moves every require together. `make modgraph-check` enforces module paths (`github.com/zenta-dev/zever/<reldir>`), except out-of-tree proofs (`docs/examples`, `examples/external-sms`).

Pre-1.0, any `0.x` minor or patch may break. Breaks are listed in `CHANGELOG.md` with a `**Breaking:**` prefix. See [Upgrade](../../guides/operate/upgrade/).

## Consume without replaces

Per-module tags resolve through the Go module proxy. Consumers need no `replace` directives:

```sh
go get github.com/zenta-dev/zever/config@v0.8.0 github.com/zenta-dev/zever/container@v0.8.0
go mod tidy
```

Rules for a healthy consumer `go.mod`:

- Keep every `github.com/zenta-dev/zever/*` require on the same version. Mixed versions are untested and unsupported.
- `go mod tidy` must succeed with no `replace` at a local checkout (`zever new` writes plain requires. Local replaces appear only when scaffolding inside a framework checkout, see [Installation](../installation/)).
- `go install github.com/zenta-dev/zever/cmd/zever@vX.Y.Z` works from v0.7.2 on (`cmd/zever/go.mod` has no `replace`). Earlier tags and library modules need the installer or a release binary.

`zever new` scaffolds a project following these rules. See [Upgrade](../../guides/operate/upgrade/).
