Install the `zever` CLI with the one-line installer, then add the Zever modules to your project with `go get`. A fresh install needs no config file and no database server.

| Requirement | Version | Notes |
|---|---|---|
| Go | 1.27.0+ | `go 1.27.0` in `go.mod`; required but not installed by the script |
| Git | any recent | needed for `go get` and scaffolding |
| Node.js | 18+ | docs site only (`docs/`), not needed for backend work |

## Install the CLI with the one-line installer

<Steps>

1. Check your toolchain. The installer does not install Go: you need `go1.27` or newer, otherwise install it from [go.dev/dl](https://go.dev/dl/).

   ```sh
   go version
   git --version
   ```

2. Install `zever` plus the matching `zever-lsp` with the pinned installer (never `main`).

   <Tabs syncKey="os">
   <TabItem label="Linux">

   ```sh
   curl -fsSL https://raw.githubusercontent.com/zenta-dev/zever/main/install.sh | sh
   ```

   </TabItem>
   <TabItem label="macOS">

   ```sh
   curl -fsSL https://raw.githubusercontent.com/zenta-dev/zever/main/install.sh | sh
   ```

   </TabItem>
   <TabItem label="Windows">

   ```powershell
   irm https://raw.githubusercontent.com/zenta-dev/zever/main/install.ps1 | iex
   ```

   </TabItem>
   </Tabs>

   <Aside type="tip" title="PATH">
   The installer puts both binaries in `~/.local/bin`. If `zever` is not found, add that directory to your `PATH`.
   </Aside>

   <Aside type="caution" title="Windows execution policy">
   If PowerShell blocks the script, download it first, then run `Unblock-File install.ps1` or invoke it with `powershell -ExecutionPolicy Bypass -File install.ps1`.
   </Aside>

3. Run `zever --help`. It prints the grouped command map (Scaffolding, Inspection, Runtime, Database, Operations).

</Steps>

<Aside type="note" title="Re-running the installer upgrades in place">
If `zever` already exists, `install.sh` upgrades it in place: older installs ask for confirmation, re-running the same version skips, and downgrading from a newer install asks for confirmation. Non-interactive shells need `--yes`. `zever-lsp` is always matched to the CLI version (it has no version flag).
</Aside>

## Add the modules to your project

Create a module and fetch the Zever modules you need at the same pinned version.

```sh
go mod init example.com/myapp
go get github.com/zenta-dev/zever/config@v0.6.1 github.com/zenta-dev/zever/container@v0.6.1 github.com/zenta-dev/zever/adapters/db/sqlite@v0.6.1
```

<Aside type="caution" title="No `go install` for zever modules">
`go install <module>@version` does NOT work for zever modules because the repo commits `replace` directives. Use the installer above or a prebuilt release binary instead.
</Aside>

## Verify with a smoke test

Build one container from `config.Default()` and resolve the database. The default `db` adapter is `sqlite`, so the check imports that adapter and calls its `Register()`. An unregistered adapter fails with `UnknownAdapterError`.

```go title="main.go"
package main

import (
	"fmt"

	"github.com/zenta-dev/zever/adapters/db/sqlite"
	"github.com/zenta-dev/zever/config"
	"github.com/zenta-dev/zever/container"
)

func main() {
	sqlite.Register()
	c := container.New(config.Default())
	db, err := c.DB()
	if err != nil {
		panic(err)
	}
	fmt.Println("db resolved:", db != nil)
}
```

```sh
go build ./... && go test ./... && go run .
```

Expected output:

```text
db resolved: true
```

If that line prints, fetch, build, and default resolution all work. `container.New(nil)` is valid too and closes cleanly. When you add a config file later, see the [configuration guide](../../guides/operate/configuration/): files use snake_case keys, and env vars are `<SERVICE>_<FIELD>` with no prefix (`DB_ADAPTER`, `DB_MAXCONNS`).

## Upgrade

Re-run the pinned installer, or self-update from the CLI itself:

```sh
zever upgrade
```

Use `zever upgrade --check` to see whether a newer release exists without installing it, and `zever upgrade --version vX.Y.Z` to pin the target instead of latest.

## Uninstall

```sh
zever uninstall
```

It removes both the `zever` and `zever-lsp` binaries. Pass `--keep-lsp` to leave the language server behind, or `--dry-run` to preview what would be removed.

## Production notes

- Pin the CLI to the same version as the modules so the TUI and backend behave alike.
- Never log raw option maps. Print `config.RedactedServices(cfg)` instead.
- `Default()` ships a deterministic dev crypto key. Never let it reach production: supply real secrets through a file or env.
- Close every container you open (`c.Close(ctx)` with a timeout parent), even in smoke tests.

## Work on Zever itself

If you contribute to the Zever repository, these `make` targets exist only in a checkout of Zever, not in a scaffolded project.

<details>
<summary>Make targets and focused test commands</summary>

| Target | What it does |
|---|---|
| `make setup` | Install the pinned lint and vuln tools (once) |
| `make build` / `make test` | `go build ./...` / `go test ./...` |
| `make test-race` | `go test -race ./...` (run by `make check`, not the PR fast gate) |
| `make fmt` / `make fmt-fix` | Check / write `gofmt` formatting |
| `make lint` / `make lint-fix` | `golangci-lint run` with `.golangci.yml` |
| `make vet` | `go vet` (a separate CI step, since `go test` runs with `-vet=off -count=1`) |
| `make vulncheck` | `govulncheck` scan |
| `make tidy-check` | `go mod tidy -diff` |
| `make generate` | `go run ./tools/gengrammar` after touching `token.Keywords` or `resolver.ScalarTypeNames` |
| `make check` | Full local CI mirror: download, fmt, vet, tidy-check, lint, test-race, vulncheck, build |

```sh
go test ./orm/...
go test ./container/... -run TestName -v
go test -race ./config/...
```

</details>

## Troubleshooting

<details>
<summary>`go version` reports older than 1.27</summary>

Cause: a stale toolchain is first on `PATH`. Fix: install Go 1.27+ from go.dev/dl and run `go version` again.
</details>

<details>
<summary>`go get` fails with a network or proxy error</summary>

Cause: an offline sandbox or a blocked `GOPROXY`. Fix: set `GOPROXY` per your site policy, run `go mod download`, then retry `go get`.
</details>

<details>
<summary>`make setup` fails while installing the lint tools</summary>

Cause: the pinned tool download was blocked or partial. Fix: re-run `make setup`, check the binaries are on `PATH`, then run `make build`.
</details>

<details>
<summary>`zever` is not found or prints nothing useful</summary>

Cause: the binaries landed in a directory outside `PATH`. Fix: add `~/.local/bin` to `PATH`, or re-run `curl -fsSL https://raw.githubusercontent.com/zenta-dev/zever/main/install.sh | sh`.
</details>

<details>
<summary>`go install ...@version` fails with a replace-directive error</summary>

Cause: expected — the repo commits `replace` directives, so `go install <module>@version` does not work for zever modules. Fix: use the installer above or a prebuilt release binary instead.
</details>

<details>
<summary>The smoke test panics resolving `DB()`</summary>

Cause: broken local state or edited defaults. Fix: remove any config file and env overrides so `config.Default()` applies, run `go run .`, then layer config back in.
</details>
