---
title: Crypto
description: Local encryption and signing with a deterministic dev key.
---

Any service that stores something sensitive — a session token, a webhook
payload, a field you don't want readable straight out of the database — needs
somewhere to encrypt and sign it that isn't hand-rolled per call site.
`crypto.Crypto` is that one place, and because `config.Default()` ships a
deterministic dev key, tests exercise real encryption without any setup.

For named credentials themselves (API keys, connection strings), see
[Secrets](/zever/digging-deeper/secrets/) — `crypto` and `secrets` solve
different problems and are resolved independently.

## Config

```yaml
crypto:
  adapter: local
  options:
    key: MDEyMzQ1Njc4OTAxMjM0NTY3ODkwMTIzNDU2Nzg5MDE=
```

```sh
CRYPTO_KEY=prod-base64-key-here
```

`local` is the only adapter today, so there's no adapter-choice decision to
make — the decision that matters is the key.

## Resolve

```go
c := container.New(config.Default())
cr, err := c.Crypto()
if err != nil {
	// handle
}
_ = cr
```

## Adapters

| Adapter | Package | Notes |
|---|---|---|
| `local` | `crypto/local` | Only adapter; dev key built in |

## The gotcha: the default key is deterministic, and that's the point — in dev

`config.Default()`'s built-in key exists so tests and local runs get real
encryption behavior without any setup — but it's the same key for everyone who
has ever run `config.Default()`, which makes it exactly as public as this
sentence. Shipping it to production would mean anything encrypted under it is
recoverable by anyone who's read this page. Supply a real key via file or
environment before you deploy; `CRYPTO_KEY` never appears in logs or errors
once you do.
