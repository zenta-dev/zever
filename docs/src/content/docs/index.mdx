## Purpose + When to use

zever fits Go backends that repeat the same plumbing on every service: database pools, cache clients, queue connections, routing, auth middleware, and typed config. Use it when you want that plumbing compiled from one schema and resolved through one container, while your handlers keep full control of business logic.

Use it for CRUD services, workers, and schedulers that share one config shape across dev and prod. Skip it for single-file scripts or services where hand-wired stdlib already covers every need with no shared infrastructure.

## Prerequisites and mental model

Three ideas carry the whole framework:

```text
.zen schema  ->  compile  ->  generated plumbing  ->  container resolves it
config file  ->  Load     ->  one Config          ->  container.New(cfg)
adapter name ->  config   ->  registry lookup     ->  cached instance
```

You need Go 1.27 or newer and a module rooted at `github.com/zenta-dev/zever` semantics (single `go.mod`, no nested modules). No Node, Docker, or database server is needed for the default path: `config.Default()` picks zero-infra adapters (sqlite, memory, log) so the first build and test run pass on a clean machine.

## Config

Every page in this site returns to the same layering: `defaults < file < env`. A minimal file plus two env overrides:

```yaml
# zever.yaml
db:
  adapter: sqlite
  options:
    path: data/app.db
log:
  adapter: slog
cache:
  adapter: memory
```

```sh
DB_ADAPTER=sqlite
DB_MAXCONNS=10
AUTH_JWT_SECRET='dev-only-secret-at-least-32-bytes-long'
```

Files are strict (unknown services or snake_case fields fail the load). Env is best-effort (stray variables such as `PATH` are ignored; only unparsable values for resolved fields return `InvalidOptionsError`). Full detail lives in `getting-started/configuration/`.

## Resolve via container

One container per process is the sole resolver. Accessors are lazy and retry on error:

```go
package main

import (
	"fmt"

	"github.com/zenta-dev/zever/config"
	"github.com/zenta-dev/zever/container"
)

func main() {
	c := container.New(config.Default())
	defer c.Close(nil)

	db, err := c.DB()
	if err != nil {
		panic(err)
	}
	fmt.Println("db resolved:", db != nil)
}
```

`container.New(nil)` is valid and closes cleanly. `Close(ctx)` shuts down only services already resolved, in dependency order. See `architecture/container/` for the full accessor table and close probing order.

## Runnable example

Describe an entity and a service once, in a `.zen` file:

```zen
entity User {
  id: uuid @primary
  email: string @unique
  created_at: timestamp @default(now())
}

service UserService {
  rpc GetUser(id: uuid) -> User {
    http: GET "/v1/users/{id}"
    auth: required
  }
}
```

Compile it, then run the smoke test:

```sh
go get github.com/zenta-dev/zever
zever compile
go run .
```

Expected output or behavior:

```text
db resolved: true
```

No database server starts and no migration runs. The default sqlite adapter opens in-process, the memory cache needs no connection, and `zever compile` only emits generated plumbing next to your schema. When the output prints, the install, schema pipeline, and container path all work.

## Variants

| Path | Command or adapter | When to pick it |
|---|---|---|
| Zero-infra dev | `sqlite`, `memory`, `log`, `noop` defaults | First run, unit tests, docs examples |
| Postgres service | `db.adapter: postgres` with `dsn` | Prod reads and writes, connection pooling |
| Redis backing | `cache.adapter: redis`, `queue.adapter: redis` | Shared cache or queue across processes |
| HTTP driver | `router.adapter: fiber` or `stdhttp` | Fiber routing features vs stdlib-only deploys |
| Compiler backends | `zever compile --backend=zenorm,openapi,atlas` | Typed ORM, OpenAPI, and DDL from one schema |
| Worker process | `c.Job()` plus `c.Scheduler()` | Jobs and cron sharing one queue connection |

Swapping a row is a config edit, never a rewrite: handlers keep calling `c.DB()` and `c.Cache()` while the registry returns the new driver. The todo and bookings examples (`examples/todo/README.md`, `examples/bookings/README.md`) show the same code running on sqlite locally and postgres in prod.

## Production notes

Close order on `SIGTERM` is: stop the HTTP server first (`srv.Shutdown(ctx)`), then `c.Close(ctx)` with a timeout parent (10s is the documented shape). Dependents holding a queue reference (`scheduler`, `job`) close first; leaf dependencies (`cache`, `queue`) close last; failures join with `errors.Join`.

Never log raw option maps: print `config.RedactedServices(cfg)` instead, which masks secrets and names services and fields only. Ship real secrets via file or env (`AUTH_JWT_SECRET`, provider `secret_key`), because `Default()` crypto keys are deterministic and public. `zever tinker` evals arbitrary Go against a live container and stays dev-only; `zever dev` is local watch mode only, never a prod supervisor.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| `go run .` prints a JWT or crypto validation error | `Default()` dev secrets were overridden with an empty value, or `doctor` runs against zero-infra defaults without env | Export `AUTH_JWT_SECRET` with at least 32 bytes for the real path; keep `Default()` for tests only |
| `config.Load` fails with unknown field | File key uses a pre-rename flat spelling (`maxconns`, `apikey`) or a typo | Rename to strict snake_case (`max_conns`, `api_key`); check `CHANGELOG.md` for the rename list |
| `c.Close` reports `CloseTimeoutError` or `ClosePanicError` at shutdown | An adapter blocked past its bound or panicked during close | Give the parent context a deadline, check adapter `Close`/`Stop` impl, match with value-type `errors.As` targets |
| `zever` with no subcommand hangs a script | Bare invocation contract misunderstood | It prints usage to stderr and exits 1 by design; always pass an explicit subcommand in scripts |
