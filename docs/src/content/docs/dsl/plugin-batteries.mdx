title: Plugin batteries in .zen
description: Proposal for referencing RegisterPlugin batteries from .zen schemas, alternatives, and boundary recommendation.
---

## Purpose

Decide how, or whether, `.zen` schemas should reference a plugin battery
registered via `container.RegisterPlugin` / `config.Plugins` (see
`docs/writing-a-plugin.md`). Today the answer is "they cannot": the resolver
knows zero battery vocabulary. This page proposes the shape such a reference
could take, evaluates invasiveness against the current resolver pipeline,
and recommends keeping the boundary for now.

When to use: planning `.zen` support for a concrete plugin battery with a
real user. When not to use: modeling core-battery domains, `entity`,
`service`, `job`, `schedule`, `message`, `enum` already cover those.

## Status

Proposal only. No compiler change ships with it. The existing boundary
(`.zen` cannot reference plugin batteries, a scope boundary, not a bug)
stands until a concrete user signs off on one of the open questions below.

## Background: how batteries resolve today

- Core batteries (`core/<b>` interface + `Register`/`Open`, container sole
  resolver) have **no resolver vocabulary**. The only battery-adjacent
  string the compiler sees is `job`'s `queue:` name, and
  `dsl/resolver/resolver_job.go:38-41` deliberately does **not** validate it
  against registered queue adapters, queue existence is a runtime/container
  concern with no compile-time visibility.
- `dsl/resolver/resolver_schedule.go:54` applies the same logic to
  `dispatch:`, cross-module dispatch is allowed because enqueueing onto a
  shared queue topic is not a DB-ownership violation.
- `dsl/resolver/boundary.go` (`CheckCrossModule`) enforces module ownership
  for relations, RPC params/returns, and permission resources. Schedules are
  intentionally exempt.
- Plugins live entirely at runtime: `config.Config.Plugins`
  (`map[string]Service[json.RawMessage]`, opaque until a validator is
  registered) plus `container.RegisterPlugin` / `Resolve` (versioned by
  `container.PluginAPIVersion`). The compiler never imports runtime
  packages (`dsl/` is compiler-internal by design).
- Pipeline order (`dsl/resolver/resolver.go:ResolveWithSchemaDir`):
  Pass -1 modules → Pass 0 symbols (`resolver_symbols.go`, flat global
  namespace across all six decl kinds) → enums → entities → messages →
  relations/indexes → services (`resolver_service.go` auth/permission) →
  jobs → schedules → opinions (`validate-everything-in`, `secure-everything`,
  cross-module) → version-drift lint.

Consequence: any `.zen` reference to a plugin battery must either be
**opaque to the resolver** (a name recorded, checked at runtime) or the
resolver must learn a **plugin type registry**, a compile-time dependency
on runtime code that the architecture explicitly forbids.

## Proposal A: schema-level `uses` declaration (deferred check)

```zen
uses sms;

entity Order {
  id: uuid @primary
  phone: string @validate(format: "phone")
}
```

- `uses <name>;` declares "this schema expects a plugin battery named
  `<name>` at runtime". The resolver records the name per module
  (`ir.Module.Uses: []string` or `ir.Schema.Uses`) and validates shape only:
  non-empty, identifier-shaped, no duplicates. It never resolves `<name>`
  to a Go type, adapter, or option schema.
- The runtime check happens where plugins already resolve: generated `app.go`
  (or hand wiring) calls `container.RegisterPlugin` / `Resolve` for each
  listed name and fails fast with a missing-plugin diagnostic naming the
  `.zen` position.
- Optional narrow follow-up: allow a field attribute to name the plugin it
  flows through (e.g. `phone: string @via(sms)`), resolved only as "the
  referenced `uses` name exists in this compile". No per-plugin type
  knowledge.

Why this shape: mirrors the `queue:` precedent (stringly-typed reference,
runtime owns truth), keeps the parser panic-free contract (one bad `uses`
line diagnoses and continues), and adds no compile-time import of plugin
code.

## Proposal B: plugin-shipped schema-fragment file

The plugin ships a `.zen` fragment (e.g. `sms.zen` declaring
`message SmsPayload { ... }`) that schemas import or the build concatenates.
The compiler resolves the fragment like any other file; the plugin's Go
code agrees by convention to honor the fragment's shape.

- Pro: reuses all existing machinery (messages, params, enums) with zero
  grammar change.
- Con: no machine-checked link between fragment and Go implementation,
  drift is silent; versioning the fragment against the plugin module is
  unsolved; dir-derived module assignment (`resolver_module.go`) makes
  "import a fragment" awkward (there is no import statement today, only
  file-set concatenation with global name uniqueness in Pass 0).

## Proposal C: typed plugin registry in the resolver

`resolver.RegisterPluginType(name, fieldTypes...)` lets plugins teach the
compiler their surface; field types like `sms.PhoneNumber` resolve against
it. Rejected: breaks the `dsl/`-never-imports-runtime boundary, introduces
global registry state (repo convention: no globals / no `init` wiring),
splits diagnostics between compile-time and runtime registries, and forces
every backend (`gogen`, `zenorm`, `proto`, `openapi`, `protogogen`),
`format`, `breaking`, the LSP, and the editor grammars to learn the new
type universe. Highest cost, least reversibility.

## Invasiveness of Proposal A

"Just" accepting `uses <name>;` touches every layer the grammar-fingerprint
tests pin:

1. `dsl/token/token.go`: new `USES` kind + `Keywords["uses"]` entry.
   `uses` becomes reserved, any field/message/enum named `uses` breaks.
2. `dsl/ast`: new decl node (`UsesDecl` + `File` accommodation).
3. `dsl/parser/parser.go`: new `parseTopLevelDecl` arm, `syncTopLevel`
   trigger set, depth-guard/recovery coverage, fuzz seeds.
4. `dsl/resolver`: Pass -1/0 handling (is `uses` per-module or per-file?
   does it participate in the duplicate-decl namespace?), new `ir`
   surface (`Module.Uses` or `Schema.Uses`), opinion/lint interaction.
5. `dsl/format`: round-trip rendering of the new decl.
6. `dsl/breaking`: is adding/removing `uses` additive or breaking?
7. `tools/gengrammar` + `make generate`: keyword table change regenerates
   `editors/nvim/syntax/zen.vim`,
   `editors/vscode/syntaxes/zen.tmLanguage.json`; LSP completion/hover
   wants the new decl.
8. Golden fixtures: `dsl/compile/testdata/app.zen` must keep passing
   unchanged; new testdata + resolver/compile tests for `uses` (valid,
   duplicate, malformed, empty-name cases).

That is a cross-cutting grammar change, not a small additive resolver
tweak. There is no resolver-only slice: the parser rejects `uses ...`
before the resolver ever runs, so "accept without full type knowledge"
still requires steps 1–3 plus IR plumbing to be observable at all.

## Recommendation: keep the boundary (no `uses` yet)

- No concrete user exists: zero battery vocab in the resolver, no plugin
  author has asked for schema-level references, and `writing-a-plugin.md`
  already documents the supported pattern (model the domain in `.zen` as
  usual, wire the plugin in Go via config + container outside the schema).
- Cost is disproportionate to demand: a reserved-word grammar change with
  resolver/IR/format/breaking/LSP/grammar fallout, plus a new reserved word
  that can never be unreserved, for a feature with no committed consumer.
- The deferred-check half of Proposal A buys little over status quo: a
  lintable manifest of plugin names is nice, but `zever.yaml`'s plugin
  section plus `app.go`'s `RegisterPlugin` calls already are that manifest
  (see the no-manifest third-party pattern). Duplicating it in `.zen` adds
  a second source of truth to keep in sync.
- Revisit trigger: a real plugin (not the `examples/sms` dogfood) needs
  schema-visible surface, e.g. generated request validation, OpenAPI
  exposure, or queue-payload typing that cannot be expressed as
  `message` + runtime wiring. At that point implement Proposal A
  (`uses` + optional `@via`), never Proposal C.

No code ships with this proposal for exactly that reason: the minimal safe
slice does not exist, and the task scope forbids non-additive compiler
changes.

## Open questions needing human sign-off

1. Is `uses` the right syntax at all, versus a `plugin:` block label or a
   file-level attribute? `uses` reads like an import; the deferred-check
   semantics are weaker than imports promise.
2. Per-module or per-schema scope? Dir-derived modules (`resolver_module.go`)
   suggest per-module, but plugin wiring (`config.Plugins` + one
   `RegisterPlugin` call) is per-binary. Which side owns a mismatch?
3. Should `@via(<name>)` (field → plugin binding) be in scope on day one,
   or is the bare manifest enough? The manifest alone has no effect on
   codegen; `@via` is where backends would need new behavior.
4. Does removing a `uses` line count as breaking under `dsl/breaking`?
   (Analogous precedent needed: removing a `queue:` target is runtime-only
   today and invisible to `breaking`.)
5. Who generates the runtime check, `gogen` emitting `RegisterPlugin`
   calls from `Uses`, or a `zever check --plugins` flag comparing `.zen`
   `uses` against `zever.yaml`? Either is new backend/CLI surface.
6. Confirm the revisit trigger: which upcoming plugin (if any) is expected
   to need schema visibility, and what codegen output would it consume?
