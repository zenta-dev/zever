Router, ORM, and queue hot-path numbers plus repro commands. All benches are deterministic (no network, no timing assertions) in `*_bench_test.go` beside the code. In-process backends (sqlite `:memory:`, miniredis) keep them offline. Absolute ns is backend-dominated, so compare allocs/op and relative deltas.

Point-in-time snapshot, not a contract. Depends on machine, load, Go version. Re-run locally. Treat numbers older than a few weeks as stale.

## Conventions

Every benchmark lives beside the code it measures and follows these rules:

- Deterministic: no network, `time.Sleep` sync, unseeded randomness, or timing assertions. In-process backends only.
- `b.ReportAllocs()` on every benchmark.
- Setup excluded: `b.ResetTimer()` after warmup, `b.Cleanup` for teardown.
- Context: `b.Context()` (or `b.Parallel`'s implicit context), never a stored context.
- Concurrent types: a `b.RunParallel` variant with balanced per-iteration work.
- Naming: `Benchmark<Thing>`, `Benchmark<Thing>Parallel`, `Before`/`After` only for optimizations.
- Target: the module's core operation (`cache` Get/Set, `queue` Push/Pop, `codec` encode/decode, `orm` query build, `dsl` lex/parse).

All benches: `make bench` (`go test -bench=. -benchmem ./...`). Per module: `go -C <dir> test -run=NONE -bench=. -benchtime=1s -cpu=1,4 -benchmem`.

### Router re-measurement (2026-10-14) and stdhttp default

Re-ran fiber benches on the same machine class after the `newHTTPHandler` rework (mirrors `gofiber/adaptor.FiberApp` minus body buffering and `RemoteAddr` resolution), plus `stdhttp` for comparison. Medians of 3 runs, `-benchtime 1s`:

| Benchmark | ns/op (cpu=1) | B/op | allocs/op |
| --- | --- | --- | --- |
| fiber `BenchmarkServeHTTP` | ~5,300 | ~4,700 | 46 |
| fiber `BenchmarkServeHTTPAdaptor` (no-op handler) | ~3,700 | ~4,080 | 35 |
| fiber `BenchmarkServeHTTPParallel` | ~8,200 / ~4,800 (cpu=4) | ~9,800 | 55 |
| stdhttp `BenchmarkServeHTTPParam` | ~1,900 / ~1,500 (cpu=4) | 2,072 | 17 |
| stdhttp `BenchmarkServeHTTPStatic` | ~1,100 / ~970 (cpu=4) | 1,010 | 10 |
| stdhttp `BenchmarkServeHTTPParallel` | ~4,100 / ~3,100 (cpu=4) | ~7,190 | 26 |

Takeaways:

- `stdhttp` is the default (and `zever new` scaffold default): param path is 17 vs 46 allocs/op (~2.7x fewer), ~3x faster here. The gap is the `fasthttpadaptor` conversion plus header/status/body merge-back paid by every fiber request.
- The old "45-55 allocs/op adaptor cost" is stale for the isolated adaptor (now 35). 45-55 still brackets full `ServeHTTP` (46) through concurrent (55).

Reproduce:

```sh
go test -run=NONE -bench='BenchmarkServeHTTP$|BenchmarkServeHTTPAdaptor|BenchmarkServeHTTPParallel' -benchtime=1s -cpu=1,4 -benchmem ./adapters/router/fiber/
go test -run=NONE -bench='BenchmarkServeHTTPParam|BenchmarkServeHTTPStatic|BenchmarkServeHTTPParallel' -benchtime=1s -cpu=1,4 -benchmem ./adapters/router/stdhttp/
```

## Repro

1. Check out the same commit and ensure `go.work` resolves (`go env GOWORK`).
2. Run the commands above, each prints `goos`/`goarch`/`cpu` lines identifying the machine.
3. Compare with `benchstat` across runs (`-count=5`) before claiming a regression or win, single-run ns/op differences under ~5% are noise.

## Slim CLI (`zever build --adapters`, 2026-10-14)

`zever build --adapters=a,b` compiles a slim CLI with only selected adapters (bare battery = all its adapters, `battery/adapter` = one pin, empty = full CLI). Unselected packages leave via a `go build -overlay` of `cmd/zever/adapters.go`. No build-tagged variants. Unknown names list the choices. The `doctor` meta-check scopes to enabled batteries, so a slim binary passes its own `doctor` (smoke-check with `<out> doctor`).

Measured here (Go 1.27.2, linux/amd64, warm cache, medians of 5 `--help` spawns. Wall time varies, ranges across two sessions):

| Binary | Size | Warm `--help` |
| --- | --- | --- |
| Full CLI (`go build ./cmd/zever`) | 309.7 MB | ~40-56 ms |
| Slim floor (`--adapters=log,router`: 4 log + 2 router adapters) | 63.3 MB | ~27-38 ms |

Floor is ~80% smaller (~5x), ~32% faster to start. Savings are excluded transitive deps (pgx, go-redis, fasthttp, otel, cloud SDKs). In-process `--help` (~99 µs/op) is unchanged. The delta is mapping plus init, not dispatch.

Repro: `go build -o /tmp/zever-full ./cmd/zever && /tmp/zever-full build --adapters=log,router --out /tmp/zever-slim && ls -lh /tmp/zever-full /tmp/zever-slim`, then `printf 'LOG_MIN_LEVEL=1\n' > /tmp/slimdemo/.env && /tmp/zever-slim doctor` (exit 0, all OK).
