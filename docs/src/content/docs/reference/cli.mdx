## Purpose

`zever` is a flags-only toolkit shell. Every command has an exact invocation, run `zever --help` for the grouped map. It scaffolds, inspects, runs, migrates, and documents projects. Project code stays in Go and `.zen`, the CLI drives it.

## Prerequisites

- Install the CLI (`go install .../cmd/zever@vX.Y.Z` works from v0.7.2 on). See [Installation](../../start/installation/):

```sh
curl -fsSL https://raw.githubusercontent.com/zenta-dev/zever/main/install.sh | sh
```

- `zever --help` prints the grouped map (Start / Build / Data / Run & ops, plus extras).

## Config

Global flags apply to every command:

```sh
zever --quiet <command>     # suppress hints/tips on stderr; errors still print
zever --no-color <command>  # disable styled output
zever --json <command>      # machine-readable JSON envelope (also ZEVER_JSON=1)
zever -V                    # print the CLI version (alias for --version)
```

`zever --help --agent` prints the agent-friendly map.
Structured `--json` `data` comes from inspection commands
(`compile`, `check`, `explain`, `doctor`, `routes`, `config show`,
`graph`, `breaking`, `check-boundaries`) plus `outbox`, `upgrade`,
`uninstall`. Others emit a JSON error envelope on failure.
`doctor --json` reports `ok:false` with a nonzero exit when any battery
fails.
File/database writers (`new`, `add`,
`extract`, `generate *`, `db migrate`, `db rollback`, `upgrade`,
`uninstall`) accept `--dry-run` to preview without applying.

`--no-color` is also honored via `NO_COLOR` / `TERM=dumb`. One-shot prompts: `-i` / `--interactive` (before or after the subcommand) or `ZEVER_INTERACTIVE=1|true|yes` enables `huh` prompts. `zever <command> -h` prints flags without running.

Bare `zever` (no subcommand, TTY or not) prints usage to stderr plus `zever: missing subcommand` and exits 1, so scripts never hang. Errors go to stderr, stdout stays clean.

## Resolve

No resolver step: pick the command, pass flags, check the code.

| Code | Meaning |
|---|---|
| `0` | success |
| `1` | runtime error (message on stderr) |
| `2` | flag misuse (error on stderr, no usage dump) |

`--help` goes to stdout, errors and bare-invocation usage to
stderr.

## Runnable example

```sh
zever --help
zever completion bash > /tmp/zever.bash
zever docs --dir /tmp/zever-docs
ls /tmp/zever-docs
echo exit:$?
```

Expected output:

```text
grouped command map on stdout (Scaffolding / Inspection / Runtime / Database / Operations)
completion script at /tmp/zever.bash
one man page plus one markdown file per command under /tmp/zever-docs
exit:0
```

Schema loop example:

```sh
zever fmt --write schema/
zever check schema/
zever compile --out ./generated
echo exit:$?
```

Expected output:

```text
fmt: normalized files listed, if any
check: silent on success
compile: per-backend output under ./generated
exit:0
```

| Tooling | `zever docs --dir <dir>` |

Legacy `queue:work`, `schedule:run`, `check:boundaries`
still work but are hidden from `--help`. Use `worker`, `schedule run`,
`check-boundaries`.

| Flag | Effect |
|---|---|
| `--quiet` | suppress hints/tips on stderr |
| `--no-color` | disable styled output |
| `--json` | machine-readable JSON envelope output (also `ZEVER_JSON=1`) |
| `-V` | print the CLI version (alias for `--version`) |
| `--dry-run` | preview file edits / SQL / removals without applying (where supported) |
| `-i`, `--interactive` | guided `huh` prompts for one-shot commands |
| `--batteries a,b` | `zever new`: extra batteries to scaffold beyond the floor (skips the battery prompt), prefer `--with` |
| `--with a,b=c` | `zever new`: batteries with optional adapter pins (replaces `--batteries`/`--adapters`) |
| `--profile minimal\|api\|full` | `zever new`: deprecated alias for `--with` |
| `--check` | `zever compile`: verify committed output matches a fresh compile, write nothing (exit 1 on drift) |
| `--strict` | `zever compile --check`: also fail when the committed files differ only in the stamped CLI version |
| `--no-tidy` | `zever compile`: print a hint instead of running `go mod tidy` when go.mod misses modules the generated code imports |
| `--adapters b=a,...` | `zever new`: per-battery adapter overrides (implies the battery, skips its adapter prompt), prefer `--with` |
| `-y`, `--yes` | `zever new`: skip all prompts, scaffold floor plus flags only, `zever add`: apply the wiring.go edit without prompting |
| `--list-batteries` | `zever new`: print the battery/default-adapter table to stdout and exit |
| `--module PATH` | `zever new`: Go module path for the new project (default: the app name itself) |
| `--dir PATH` | `zever new`: output directory (default `./<name>`) |
| `--framework-version V` | `zever new`: depend on a published Zever version instead of a local replace directive |
| `--force` | `zever new`: scaffold into a non-empty directory anyway, `zever add`: allow an adapter swap and overwrite existing recipe files |
| `--name N` | `zever add`: wire a named instance (for example `--name analytics` for `db.Ref("analytics")`) |
| `--uses R` | `zever add`: declare a boot-order edge on another wired instance (for example `--uses db`) |
| `--diff` | `zever add`: print the wiring.go diff and change nothing |
| `--project` | `zever upgrade`: upgrade the current project's go.mod instead of the binary |
| `-h` | print flags without running |

Against a local framework checkout (auto-detected or `ZEVER_FRAMEWORK_PATH`), the generated `go.mod`
replaces every module of that checkout's graph (batteries,
adapters, shared helpers and their in-repo requires), so the project
resolves against the checkout
instead of the module proxy. The set is derived from the checkout itself,
so later framework modules are covered.

### `zever add`

Adds one core battery to an existing project (exactly one positional):

```sh
zever add <battery>[/<adapter>] [--adapter NAME] [--name N] [--uses R] [--force] [--module PATH[@VERSION]] [--diff] [--yes] [--dry-run]
```

`--adapter` overrides the slash form, `--force` allows a swap and
overwrites recipes, `--module` names a plugin battery's Go
module (required for plugins), `--name` wires a named instance,
`--uses` records a boot-order edge, `--diff`
prints the diff and changes nothing, `--yes` applies without prompting,
`--dry-run` prints without writing.

The adapter may be omitted (`zever add cache` uses
`config.Default()`'s pick, e.g. `memory`) or pinned explicitly
(`zever add cache/redis`). Empty halves, extra slashes, and unknown
batteries are errors. Run from the project root (`go.mod` dir). Without one it fails.

Effects (append-only, never overwriting hand-written code):

- `internal/app/wiring.go`: a `go/ast` edit inserting the battery's `Ref`
  var, its `container.Provide` entry, and the adapter import, all idempotent, so re-adding is a no-op. Fails without a `Providers` function returning a `[]container.Provider`
  literal. Scaffold with `zever new` first.
- `.env.example`: appends the battery's env keys, including the
  `<SERVICE>__<NAME>__*` section when `--name` wires a named instance.
- `go.mod`: adds `require` entries for core and adapter
  modules at the framework-pinned version (falling back
  to the CLI's built-in version). For local checkouts (a
  `replace github.com/zenta-dev/zever => <local-dir>` marker), matching
  local replaces are derived for both modules. Paths already required
  (any version) or replaced are untouched.

`zever add` then runs `go get` and `go mod tidy`, then serve:

```sh
zever add cache/redis
zever serve
```

### `zever outbox`

Inspects and repairs the outbox dead-letter queue without starting the
relay. Every subcommand takes `--dsn` and `--table`.
Without them values come from `OUTBOX_DSN`/`OUTBOX_TABLE` plus overrides. `--json` gives
machine-readable output throughout.

| Command | Effect |
|---|---|
| `zever outbox status` | Relay counters (`pending`, `processed`, `failed`, `last_error`, `stalled`) |
| `zever outbox dlq list [--limit N]` | Failed messages, oldest first (`0` uses the adapter default page size) |
| `zever outbox dlq requeue --id X` | Requeue one failed message, resetting its attempt count and lock |
| `zever outbox dlq requeue --all` | Requeue every failed message |
| `zever outbox dlq purge --id X` | Delete one failed message by id |
| `zever outbox purge --before 168h` | Delete processed messages older than the given duration |

`--id` and `--all` are mutually exclusive, exactly one
is required. `purge --before` takes a non-negative Go duration. `dlq purge` needs
`outbox.Deleter` (only `db` implements it). Others report
`does not support message deletion`. Run
from a deploy box with database access. Metrics, alert rules, and runbook:
[Outbox Ops](../../guides/background/outbox-ops/).

### `zever uninstall`

Removes the running `zever` binary (`os.Executable()`,
symlinks followed) plus every `zever-lsp` on `PATH`.
Binaries only: projects, caches, profiles, config stay.

```sh
zever uninstall --dry-run        # print the removal plan, delete nothing
zever uninstall --yes            # confirm without prompting
zever uninstall --keep-lsp --yes # leave zever-lsp in place
```

Without `--yes`/`--force`, a terminal gets `[y/N]` (default
No). Headless fails, printing the exact
`zever uninstall --yes` re-run. On Windows the binary cannot
self-delete, so it becomes a printed `del "<path>"` step.
`zever-lsp` removals stay automatic. `--json` emits the
envelope, not the human plan.

### `zever upgrade`

Upgrades the running `zever` binary to latest stable (or
`--version X`). Current version is the compiled
`cliVersion`. Default target comes from
`api.github.com/repos/zenta-dev/zever/releases/latest`.

```sh
zever upgrade --check              # print the available version, exit 0
zever upgrade --dry-run            # print the upgrade plan, download nothing
zever upgrade --yes                # confirm without prompting
zever upgrade --version v0.7.0 --yes
zever upgrade --project --dry-run  # plan the project's go.mod upgrade instead
```

`--project` upgrades the project's `go.mod` instead of the binary:
rewrites every framework require (third-party
and `replace`-pinned stay untouched), prints the `**Breaking:**` notes in between,
then tidies. Needs a `go.mod` with a framework require. The binary is untouched.

Versions compare with `golang.org/x/mod/semver`: current
targets print `already current` (exit 0). Older targets refuse
unless `--version` requested them. The `GOOS`/`GOARCH` asset
(`.exe` on Windows) plus `SHA256SUMS.txt` downloads from the
release, verified with `crypto/sha256`. Mismatch
or network error aborts before replacement. POSIX installs
atomically (temp file, `chmod +x`, rename over
the binary). Windows stages `zever.new.exe` and
a detached `cmd /C` helper swaps it after
exit. Restart the shell. Confirmation follows
`uninstall` TTY rules. `--json` emits the envelope.

### Dev and tinker rules

- `zever dev` is local watch-only: prints
  `zever dev: watching <schemaDir> and <serverEntry> … (Ctrl-C to stop)`
  and restarts the entrypoint on change. Ctrl-C stops both. Never a deployment path.
- `zever tinker` is dev-only: every start prints
  `WARNING: Zever tinker is development-only: it evaluates arbitrary Go
  against a live container, so run it against a development database only.`
  to stderr. The REPL uses the per-project shim
  (`ZEVER_TINKER_ENTRY`, default
  `cmd/tinker-shim`, scaffold with `zever generate tinker`). Never point it
  at production data.

### Shell completion and generated docs

- `zever completion <shell>` prints that shell's script to
  stdout (e.g. `zever completion bash > /etc/bash_completion.d/zever`). Scripts
  complete `.zen` files, `generate` kinds, `--backend` lists, `--profile`, `--adapters`
  (`battery=adapter` for `new`, `battery` or `battery/adapter` for `build`).
- `zever docs --dir <dir>` writes one man page plus one markdown per
  command. Stripped releases via
  `make build-release` (`-trimpath -ldflags="-s -w"`).
- `migrate` / `rollback` mask the DSN (`--dsn ***`) in display and output.

## Production notes

- Script against exit codes, not text: `0` / `1` / `2` are the
  contract, hints may change (`--quiet` suppresses them).
- Keep stdout parseable: errors never touch stdout, so pipes and
  `$(...)` stay clean.
- `dev` and `tinker` never run in prod: watch-only and arbitrary-Go eval. Gate both out of images.
- Pin the CLI version to the repo release. Flag surfaces move
  with releases.

## Troubleshooting

- **Bare `zever` exits 1**: expected. Usage plus
  `zever: missing subcommand` on stderr. Pass a subcommand or `--help`.
- **Exit 2 with no usage dump**: flag misuse. Re-check spelling with
  `zever <command> -h`.
- **`tinker` warns on every start**: by design on stderr. Do not silence or point at prod data.
- **`dev` does not restart on edits**: it watches schema dir and server
  entrypoint only. Other paths need a manual restart.
- **Styled output garbles CI logs**: pass `--no-color` or set
  `NO_COLOR=1` (`TERM=dumb` works too).
- **`zever outbox` reports empty counters**: resolved `--table`
  mismatches the relay table. Compare against
  `OUTBOX_TABLE`.
- **`zever outbox dlq purge` says deletion is unsupported**:
  only `db` implements `outbox.Deleter`. Switch the
  connection, not the command.
