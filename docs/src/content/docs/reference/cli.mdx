## Purpose

`zever` is a flags-only toolkit shell. Every command has an exact CLI
invocation; run `zever --help` for the grouped command map.

When to use: scaffold, inspect, run, migrate, and document a zever
project. When not to use: project code stays in Go and `.zen`; the CLI
drives it, never hosts logic.

## Prerequisites

- Install the `cmd/zever` module (multi-module repo: `core/<b>` = battery interface + `Register`/`Open` registry, `adapters/<b>/<a>` = one module per adapter with `Register()`, `shared/*` = SDK-free helpers):

```sh
go install github.com/zenta-dev/zever/cmd/zever@v0.5.0
```

- `zever --help` prints the grouped map (Scaffolding / Inspection /
  Runtime / Database).

## Config

Global flags apply to every command:

```sh
zever --quiet <command>     # suppress hints/tips on stderr; errors still print
zever --no-color <command>  # disable styled output
```

`--no-color` is also honored via ambient `NO_COLOR` / `TERM=dumb`. Guided
prompts for one-shot commands: `-i` / `--interactive` (before or after the
subcommand) or `ZEVER_INTERACTIVE=1|true|yes` enables `huh` prompts.
`zever <command> -h` always prints flags without running anything.

Bare-command contract: bare `zever` (no subcommand, TTY or not) prints
usage to stderr plus `zever: missing subcommand` and exits 1, so scripts
never hang. All errors go to stderr; stdout stays clean for command
output.

## Resolve

No resolver step: pick the command, pass flags, check the exit code.

| Code | Meaning |
|---|---|
| `0` | success |
| `1` | runtime error (message on stderr) |
| `2` | flag misuse (error on stderr, no usage dump) |

`--help` output goes to stdout; errors and bare-invocation usage go to
stderr.

## Runnable example

```sh
zever --help
zever completion bash > /tmp/zever.bash
zever docs --dir /tmp/zever-docs
ls /tmp/zever-docs
echo exit:$?
```

Expected output:

```text
grouped command map on stdout (Scaffolding / Inspection / Runtime / Database)
completion script at /tmp/zever.bash
one man page plus one markdown file per command under /tmp/zever-docs
exit:0
```

Schema loop example:

```sh
zever fmt --write schema/
zever check schema/
zever compile --out ./generated
echo exit:$?
```

Expected output:

```text
fmt: normalized files listed, if any
check: silent on success
compile: per-backend output under ./generated
exit:0
```

### `zever add`

<!-- NOTE: extend this section when --adapter/--force/plugin flags land (separate CLI task owns them). -->

Adds one core battery to an existing project. Synopsis (exactly one
positional, no prompting):

```sh
zever add <battery>[/<adapter>]
```

The adapter may be omitted (`zever add cache` selects
`config.Default()`'s own pick, e.g. `memory`) or pinned explicitly
(`zever add cache/redis`). Empty halves, extra slashes, and unknown
batteries are errors. Run it from the project root (the directory
holding `go.mod`); without one it fails.

Effects (three append-only edits, never overwriting hand-written code):

- `go.mod`: adds `require` entries for the battery's core and adapter
  modules at the version pinned by the framework require (falling back
  to the CLI's built-in framework version). For local checkouts (a
  `replace github.com/zenta-dev/zever => <local-dir>` marker), matching
  local replaces are derived for both modules. Paths already required
  (any version) or already replaced are left untouched.
- `internal/app/app.go`: splices in the adapter's named import plus its
  `Register()` call (gofmt-normalized). Either half already present is
  skipped, so re-adding the same battery is a no-op. Fails if the file
  has no import block or no `func New` — scaffold it with
  `zever generate server` first.
- `zever.yaml`: sets `<battery>.adapter`, preserving every other entry
  (including the entry's own options). A missing or empty file starts a
  fresh document (with the schema modeline, like `zever new`); an
  existing file keeps its header.

`zever add` does not run `go mod tidy` — run it afterwards so `go.sum`
catches up, then serve:

```sh
zever add cache/redis
go mod tidy
zever serve
```

### Dev and tinker rules

- `zever dev` is local watch-only: it prints
  `zever dev: watching <schemaDir> and <serverEntry> … (Ctrl-C to stop)`
  to stdout and restarts the server entrypoint on change. Ctrl-C stops the
  watcher and the server. Never a deployment path.
- `zever tinker` is dev-only: every start prints
  `WARNING: zever tinker is development-only: it evaluates arbitrary Go
  against a live container, so run it against a development database only.`
  to stderr. The REPL talks to the real container via the per-project shim
  (`project.tinker_entry`, default `cmd/tinker-shim`; scaffold with
  `zever generate tinker`). Never point it at production data.

### Shell completion and generated docs

- `zever completion <shell>` prints that shell's completion script to
  stdout; redirect into the completions dir, e.g.
  `zever completion bash > /etc/bash_completion.d/zever`.
- `zever docs --dir <dir>` writes one man page plus one markdown file per
  command into `<dir>`; build stripped release binaries with
  `make build-release` (`-trimpath -ldflags="-s -w"`).
- `migrate` / `rollback` mask the DSN (`--dsn ***`) in display and output.

## Production notes

- Script against exit codes, not output text: `0` / `1` / `2` are the
  contract; hint wording may change (and `--quiet` suppresses hints).
- Keep stdout parseable: errors never touch stdout, so pipes and
  `$(...)` capture stay clean.
- `dev` and `tinker` never run in prod: `dev` is watch-only, `tinker`
  evaluates arbitrary Go. Gate both out of deployment images.
- Pin the installed CLI version to the repo release; flag surfaces move
  with releases.

## Troubleshooting

- **Bare `zever` exits 1**: expected; it prints usage to stderr with
  `zever: missing subcommand`. Pass a subcommand or `--help`.
- **Exit 2 with no usage dump**: flag misuse. Re-check flag spelling with
  `zever <command> -h`; only the error prints.
- **`tinker` warns on every start**: by design, the dev-only warning goes
  to stderr each launch. Do not silence it; do not aim it at prod data.
- **`dev` does not restart on edits**: it watches the schema dir and the
  server entrypoint only. Edits outside those paths need a manual restart.
- **Styled output garbles CI logs**: pass `--no-color` or set
  `NO_COLOR=1`; `TERM=dumb` is honored the same way.
