This site is an [Astro](https://astro.build) + [Starlight](https://starlight.astro.build)
project living in `docs/`. To preview changes locally:

```sh
cd docs
npm install
npm run dev
```

`npm run build` produces the static site; `npm run preview` serves that build
locally.

## Writing conventions

- Every service page under **Digging Deeper** and **Security** follows the
  same loose shape: a short narrative on *why* the service exists and *when*
  to reach for each adapter, a `Config` section (YAML + env var form), a
  `Resolve` section (container accessor snippet), an `Adapters` table, and at
  least one concrete gotcha. Keep config keys, adapter names, and code
  snippets accurate to the real Go packages — verify against the package's
  `doc.go`/`options.go`/`adapter.go` before publishing, never invent a method
  signature or config key. If the package also has its own `README.md`,
  check it too: several package READMEs (`config`, `container`, `orm`,
  `cmd/zever`, `tools/zever-lsp`, `editors/*`) carry more precedence/option/
  install detail than made it into the corresponding docs page — a README
  update that isn't reflected here is a docs gap, not a duplicate.
- Code snippets should compile against the current module — copy real
  imports (`github.com/zenta-dev/zever/...`), don't abbreviate package paths.
- Cross-link related pages, e.g. a new service page should link back to
  [Adapters Matrix](reference/adapters-matrix/) and to
  [Container](architecture/container/).
