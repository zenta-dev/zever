Zever compiles `.zen` schemas into typed code and wires backends through one container: plumbing, not business logic.

## Flow

```text
 compile time                              run time
 ------------                              --------
 schema.zen -> compiler -> generated/      config -> container -> adapters
   (dsl)       lexer          ORM, routes,   defaults   lazy        db, cache,
               parser         OpenAPI, DDL   < .env     accessors   queue, ...
               resolver                      < .env.local
               backends                      < process env
```

Runtime imports only generated code, `config`, `container`, and adapters. Config is env-only (`defaults < .env < .env.local < process env`), never a file.

## Stages

| Stage | What | More |
|---|---|---|
| Schema | Entities, services, RPCs in `.zen`. | [Syntax](../../reference/zen-syntax/) |
| Compiler | Lexer, parser, resolver -> `ir.Schema`, all in one run. | [Resolver and IR](../resolver-ir/) |
| Backends | IR in, files out (ORM, protobuf, OpenAPI, Atlas HCL). | [Backends](../backends/) |
| Boundary | Compile-time only. Runtime never imports `dsl`. | [Compiler boundary](../compiler-boundary/) |
| Config | Strict layered env only. | [Configuration](../../guides/operate/configuration/) |
| Container | One per process. Lazy resolve, dependency-ordered close. | [Container](../container/) |
| Adapters | Small interfaces, swappable via `Ref` + `container.Provide`. | [Providers and adapters](../providers-adapters/) |
| Process | Load, build, resolve on first use, close. | [Lifecycle](../lifecycle/) |

## Key points

- Swap by editing `internal/app/wiring.go` and env, not call sites, with no globals or `init()`, only `container.Provide`, then rebuild. Changing `sqlite` to `postgres` or `memory` to `redis` is the typical case.
- Pay once at compile time by parsing and resolving once, request-time code stays plain Go.
