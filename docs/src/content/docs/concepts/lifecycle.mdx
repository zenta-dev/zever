Four phases per process: load config, build the container, resolve on first use, close. The phase tells you whether a failure is fail-fast, retryable, or a shutdown problem.

## The four phases

```text
config.FromEnv + Resolve  ->  container.New  ->  resolve on first use  ->  Close(ctx)
     env                       one per          c.DB(), c.Cache()...        dependents
                              process          retry on error              first, leaves later
```

Build one container per process, no globals or `init()` wiring, `container.New(nil)` is valid.

- **1. Load config**: `config.FromEnv()` reads `.env`, `.env.local`, and process env. `config.Resolve(env)` builds the typed `Config` (`config.LoadEnv(files...)` for explicit files). Defaults read `SERVICE_FIELD`, named instances read `SERVICE__NAME__FIELD` via a matching named Ref. Env is strict about keys it understands (an unknown key under a wired service prefix fails with a did-you-mean hint) and ignores the rest (unknown service heads, bare names). Invalid values fail here as `InvalidOptionsError`, not mid-request. Unwired services pass load and fail on first resolution with `NotWiredError` naming the missing `container.Provide` entry. See the [Config reference](../../reference/config/) for keys. `Default()` dev secrets belong in tests only.
- **2. Build container**: one `Container` owns future connections. `New` never dials, `nil` cfg valid.
- **3a. First resolution**: construct and cache the adapter. On error the cache clears and the next call retries.
- **3b. Steady serving**: cached instance reused per accessor, per-call errors only, no rebuild.
- **3c. Shared resolution**: `Scheduler()` resolves `Job()` then `Queue()`, one shared connection.
- **4. Close**: resolved services shut down in order, `errors.Join` of per-service errors.

## Resolve lazily and reuse

Resolve inside handlers and reuse the cached instance. A cleared cache retries instead of pinning a broken handle. `Job()` dispatches over the resolved `Queue`, `Scheduler()` shares it.

## Close in order

Stop the HTTP server first, then close the container under a timeout parent (`context.WithTimeout`, about 10s). See [Deployment](../../guides/operate/deployment/) for the full shutdown wiring. `Close` never opens anything, so an unused service cannot fail shutdown. Dependents (`scheduler`, `job`, `agent`, `rag`) close first, then leaves (`cache`, `queue`), then `db` and shared pools. Each service gets a 5s bound without a parent deadline, shared instances close once.

- **Panic during close**: `container.ClosePanicError`, the adapter panicked and shutdown continued.
- **Per-service timeout**: `container.CloseTimeoutError`, the adapter exceeded its bound.
- **Several failures**: `errors.Join`, inspect each with `errors.As`.

## Design decisions and trade-offs

Errors name the service only, never secrets (display via `config.RedactedServices`). Both close error types are values, so `errors.As` needs a value target.

## Troubleshooting

<details>
<summary>The process fails at boot before serving</summary>

An unparsable env value. The `Resolve` error names the service and field.
</details>

<details>
<summary>The first request fails but the next succeeds</summary>

A transient backend error cleared the cache. Ignore it unless it repeats.
</details>

<details>
<summary>Shutdown hangs</summary>

`Close` got a bare context while an adapter blocks. Use `context.WithTimeout` (about 10s).
</details>

<details>
<summary>`errors.As` for close errors never matches</summary>

A pointer target never matches a value type. Declare a value variable.
</details>

<details>
<summary>A goroutine leak is reported after a lifecycle test</summary>

A goroutine outlived `Close` (`go test -tags=leak ./container/`). Stop it in the adapter's `Close`.
</details>
