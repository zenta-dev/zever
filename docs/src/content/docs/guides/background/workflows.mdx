Use `workflow` for multi-step runs (onboarding, payouts, provisioning) that must survive a restart partway through. A crash after step 3 resumes at step 3 instead of starting over. The interface covers run lifecycle: `Start` a named workflow with JSON-marshalable input, `Signal` a running channel, `Query` state into an output value, and `Cancel` a run.

This is not a cron scheduler. Use the [scheduler](../scheduler-jobs/) for cron-shaped firing, and `queue` plus `job` for plain background tasks. For multi-step operations with rollback, see [saga](../saga/).

## Quick start

```yaml title="zever.yaml"
workflow:
  adapter: memory
  options:
    namespace: bookings
```

```go title="main.go"
package main

import (
	"context"
	"fmt"

	"github.com/zenta-dev/zever/config"
	"github.com/zenta-dev/zever/container"
)

func main() {
	c := container.New(config.Default())
	wf, err := c.Workflow()
	if err != nil {
		panic(err)
	}
	defer wf.Close()

	ctx := context.Background()
	id, err := wf.Start(ctx, "booking-confirm", map[string]string{"booking_id": "b-1"}, "wf-b-1")
	fmt.Println(id, err)
	var state map[string]any
	fmt.Println(wf.Query(ctx, id, "status", &state))
	fmt.Println(wf.Cancel(ctx, id))
}
```

```text
wf-b-1 <nil>
<nil>
<nil>
```

The run ID echo depends on the backend. The shape is start, query, cancel with no errors. Use `Signal(ctx, runID, name, value)` to deliver a named value to a running ID when the flow needs outside input mid-run.

`Workflow()` resolves lazily, caches per container, and retries after errors. `Workflow.Close() error` takes no context. See [the container](../../../concepts/container/).

## Choose a backend

| Adapter | Package | Use when |
|---|---|---|
| `memory` | `adapters/workflow/memory` | Default. Local dev and tests. In-process, bounded pending buffer that returns `ErrPendingFull` instead of blocking. |
| `db` | `adapters/workflow/db` | Durable DB-backed runs, lease-reclaimed steps. Needs `dsn`. |
| `postgres` | `adapters/workflow/db` | Legacy alias for `db`. |

`memory` state dies with the process, so two replicas each see only their own runs and a restart loses all of them. Anything that must survive a crash needs `db`.

Engines with host-registered steps expose them through the separate `StepRegistrar` interface (`RegisterStep`), so engines without the concept are unaffected. Step input and output must be JSON-marshalable. The output becomes queryable state, so keep payloads small and reference-backed.

## Configure the workflow

```sh
WORKFLOW_ADAPTER=memory
WORKFLOW_NAMESPACE=bookings
WORKFLOW_HOSTPORT=127.0.0.1:7233
```

`namespace` scopes runs. `host_port` names a workflow server address when the backend needs one. Both are optional for `memory`. `Validate` only rejects a malformed `host_port` (it must split as host:port when set). Everything else passes to the adapter.

A durable workflow shares the container pool for its DSN with every other battery on that DSN (first opener's `max_conns` wins). Set `dedicated_pool: true` with a separate workflow database under sustained load. All keys: [workflow config reference](../../../reference/config/#workflow).

## Production checklist

- Design every step idempotent now (locks plus idempotency keys for money-moving steps) so a durable backend can replay safely. Cap retries per step and route poison inputs to a dead-letter path.
- Inputs, signals, and step results become queryable state and may cross process boundaries. Keep secrets and PII out of them and pass references. Never log raw option maps. Use `config.RedactedServices`.
- The container closes only resolved services and joins errors via `errors.Join`. Panics become `*ClosePanicError`.

## Troubleshooting

<details>
<summary>ErrPendingFull on start</summary>

Cause: the memory pending buffer is full.

Fix: drain or cancel stuck runs, cap per-step retries, and send poison inputs to a dead-letter path rather than looping.
</details>

<details>
<summary>Query fails with a marshal error</summary>

Cause: `Start` and `Signal` store values as-is and marshal lazily at `Query` time, so a non-marshalable input surfaces there, not at start.

Fix: pass only JSON-marshalable values (maps, slices, structs without channels or funcs).
</details>

<details>
<summary>Steps re-run side effects after a crash</summary>

Cause: the step was not idempotent.

Fix: gate side-effecting steps behind `lock` singletons and idempotency keys, and emit an observability span per step so stalled runs are locatable.
</details>
