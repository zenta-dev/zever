## Purpose

After [Outbox](../outbox/) is wired. The relay fails quietly: broker outages show as pile-up, not crashes. Covers relay metric names, alert rules, the DLQ runbook, and the stalled-relay readiness gate.

## Metrics

The relay emits through the `observability.Provider` on `outbox.Options.Provider`. Telemetry is best-effort: nil provider makes every metric a no-op, metric/span errors are discarded (`_ =`) so a metrics outage can't fail a publish. Production needs the `otlp` backend in `internal/app/wiring.go`, with `OBSERVABILITY_SERVICE_NAME` and `OBSERVABILITY_ENDPOINT` (`stdout` prints locally, `noop` drops). Scope is `outbox`.

| Metric | Type | Meaning |
|---|---|---|
| `outbox.pending` | gauge | Messages awaiting publication |
| `outbox.failed` | gauge | Messages that exhausted `max_attempts` (DLQ depth) |
| `outbox.oldest_pending_age_seconds` | gauge | Age of the oldest pending message, `0` when nothing is pending |
| `outbox.published` | counter | Successful publishes (`outbox.outcome="ok"`) |
| `outbox.retried` | counter | Publish failures that will be retried (`outbox.outcome="error"`) |
| `outbox.failed_total` | counter | Messages moved to the failed state (`outbox.outcome="error"`) |
| `outbox.relay_errors` | counter | Relay-loop errors (`outbox.outcome="error"`) |
| `outbox.publish.duration_seconds` | histogram | Per-publish latency, tagged with the outcome |

The three gauges come from the `db` relay only. The `cdc` consumer keeps counters in memory and reports them via `Status()`, emitting `outbox.published`, `outbox.retried`, `outbox.failed_total`, `outbox.relay_errors` but no pending/oldest-age gauges.

Attributes carried on every metric and span:

| Attribute | Values |
|---|---|
| `outbox.adapter` | `db` or `cdc` |
| `outbox.table` | Outbox table name, `db` only, omitted when empty |
| `outbox.topic` | Message topic (on `outbox.publish` / `outbox.consume` spans) |
| `outbox.outcome` | `ok` or `error` |

Spans: `outbox.publish` (kind `producer`) per publish, paired with the duration observation, and `outbox.consume` (kind `consumer`) on the `cdc` path. Both carry OTel messaging conventions plus `outbox.*` attributes: `messaging.system` (configured `publisher` transport else adapter name), `messaging.destination.name` (topic), `messaging.operation` (`publish`/`process`), `messaging.message.id`, and `messaging.message.conversation_id` when the context carries a trace (how a relay span joins the recording trace).

Keep metric attributes bounded. `outbox.topic` is a code-level constant, but per-tenant topics grow label cardinality (and collector bills).

Prometheus reads the OTLP export, which renames dots to underscores: `outbox.publish.duration_seconds` becomes `outbox_publish_duration_seconds_bucket`, and the histogram needs a `_bucket`/`_sum`/`_count` trio plus a matching `le` label.

## Recommended alerts

Five rules covering the failures that page. Tune thresholds to your delivery SLA, the queries matter.

Backlog growing (relay slower than publishes, or stalled):

```promql
max by (outbox_table) (deriv(outbox_pending[15m]) > 0)
```

Oldest pending message past the delivery SLA:

```promql
max_over_time(outbox_oldest_pending_age_seconds[5m]) > 300
```

DLQ non-empty (something exhausted retries):

```promql
increase(outbox_failed_total[10m]) > 0
or
outbox_failed > 0
```

Relay loop erroring (claim failures, bad DSN, dropped pool):

```promql
rate(outbox_relay_errors[5m]) > 0
```

Publish latency (slow downstream before it times out):

```promql
histogram_quantile(0.99, sum by (le) (rate(outbox_publish_duration_seconds_bucket[5m]))) > 1
```

A worked rule file:

```yaml
groups:
  - name: zever-outbox
    rules:
      - alert: OutboxBacklogGrowing
        expr: max by (outbox_table) (deriv(outbox_pending[15m])) > 0
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: outbox backlog is growing
          runbook: zever outbox status, then zever outbox dlq list
      - alert: OutboxOldestPendingPastSLA
        expr: max_over_time(outbox_oldest_pending_age_seconds[5m]) > 300
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: oldest pending outbox message is older than the SLA
      - alert: OutboxDLQNotEmpty
        expr: increase(outbox_failed_total[10m]) > 0
        for: 10m
        labels:
          severity: critical
        annotations:
          summary: messages are landing in the outbox DLQ
      - alert: OutboxRelayErrors
        expr: rate(outbox_relay_errors[5m]) > 0
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: outbox relay loop is erroring
```

## DLQ runbook

Rows exhausting `max_attempts` (default 5) are marked `failed`: not deleted, not retried, waiting for a human. Work in order.

1. Confirm the shape of the problem.

```sh
zever outbox status
```

```
outbox status  table=outbox
  pending    0
  processed  14205
  failed     3
  last_error  publish booking.created: dial tcp 10.0.3.17:9092: connect: connection refused
  stalled    false
```

Add `--json` for machine-readable output. Non-zero `failed` with one destination in `last_error` is usually one bad dependency, several topics means the broker itself is down.

2. List the dead letters, oldest first.

```sh
zever outbox dlq list --limit 20
```

```
msg-01HZX...  booking.created  attempts=5  created=2026-10-06T09:14:02Z
msg-01HZX...  payment.captured attempts=5  created=2026-10-06T09:14:02Z
```

3. Read `last_error` and fix the root cause before re-driving. Requeueing into a still-broken broker burns the retry budget (check broker, credentials, topic existence, payload size). Requeue resets `attempts`.

4. Requeue one message or the whole DLQ:

```sh
zever outbox dlq requeue --id msg-01HZX...
zever outbox dlq requeue --all
```

`--id` and `--all` are mutually exclusive and exactly one is required.

5. Watch it drain, then confirm the queue is empty:

```sh
zever outbox status
zever outbox dlq list
```

6. Drop messages you won't deliver (poison payload, decommissioned consumer). Deletion is permanent, one id at a time:

```sh
zever outbox dlq purge --id msg-01HZX...
```

7. Retention is separate. `purge` deletes *processed* rows older than a cutoff, keeping the table small without touching undelivered rows:

```sh
zever outbox purge --before 168h   # processed rows older than 7 days
```

Every command accepts `--dsn` and `--table`, without them the CLI resolves from environment (`.env` / `.env.local` + process env). Run from one deploy box with database access, not every replica.

## Stalled relay readiness

`Status().Stalled` is true when pending rows don't drain: the `db` adapter sets it once the oldest pending row waited longer than `db.DefaultStallAfter` (5 minutes, `adapters/outbox/db/options.go:32-34`). Stronger than `pending > 0` (a busy relay is healthy, one holding old rows is stuck). The 5-minute default is why the SLA alert above uses `> 300`.

Readiness is opt-in. With `OUTBOX_STALL_READINESS=true` the generated server's `/readyz` returns 503 and gRPC health flips to `NOT_SERVING` while `Stalled` holds, pulling the replica out of the load balancer:

```sh
OUTBOX_DSN=postgres://app:secret@db:5432/app
OUTBOX_STALL_READINESS=true
```

The flag belongs to the `outbox` service (`OUTBOX_STALL_READINESS`), not the adapter. The check is best-effort: an unresolvable store is skipped rather than failing readiness, so the flag can't make a process without the outbox permanently unready.

Leave it off when several replicas share one outbox table and you'd rather alert than shed traffic (one slow publish must not remove a healthy replica). Watch `Stalled` via `outbox.oldest_pending_age_seconds` and the alerts above.

The same signal is available in-process when you want to gate your own traffic:

```go
import (
    "github.com/zenta-dev/zever/config"
    "github.com/zenta-dev/zever/container"
)

func relayHealthy() error {
    c := container.New(config.Default())
    ob, err := c.Outbox()
    if err != nil {
        return err
    }
    if ob.Status().Stalled {
        return errors.New("outbox relay is stalled")
    }
    return nil
}
```

## Production notes

- Multi-instance: `db` relay claims with `FOR UPDATE SKIP LOCKED` + `lock_seconds` lease, so every replica can relay one table. `Requeue` takes effect on whichever replica polls next (requeue once, not per replica).
- Redaction: `last_error` can carry broker hostnames. Treat DLQ output as sensitive, `outbox.pending` gauges carry no payload.
- Cardinality: keep topics a fixed set. Per-request topics turn `outbox.publish.duration_seconds` into a cardinality incident.
- Never delete `pending`/`failed` rows to "unstick" the relay. Fix the cause, then requeue or purge.
- The `memory` adapter emits no relay metrics worth alerting on: synchronous publish, nothing stored.

## Troubleshooting

| # | Symptom | Fix |
|---|---|---|
| 1 | No `outbox.*` metrics | Nil provider or `noop` adapter. Wire `otlp` (`OBSERVABILITY_SERVICE_NAME` + `OBSERVABILITY_ENDPOINT`), confirm store has a provider |
| 2 | `status` connects but counters empty | `--table`/`OUTBOX_TABLE` mismatch, compare with relay's `OUTBOX_TABLE` |
| 3 | `requeue` looks fine but row stays `failed` | Claim lease held elsewhere, or publish failing again pre-budget, re-check after one retry cycle |
| 4 | `does not support admin operations` / `does not support message deletion` | Only `db` implements `outbox.Admin`/`Deleter`, switch the connection |
| 5 | Pending grows but `published` grows too | Throughput-bound, not stuck: check `publish.duration_seconds` p99, raise `batch_size`/replicas, not `max_attempts` |
