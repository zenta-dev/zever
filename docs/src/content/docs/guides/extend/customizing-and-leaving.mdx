Zever generates plumbing, never business logic. This page covers owned vs generated code, standalone use, drift gating, custom backends, and leaving.

## Generated versus owned

| Path | Owner | Rule |
|---|---|---|
| `schema/*.zen` | You | The single source of truth. Everything else derives from it. |
| `generated/*` | Compiler (`zever compile`) | Never hand-edit. Regenerate, or gate drift (below). |
| `internal/app/wiring.go`, `cmd/*`, `db/seed/*` | You after eject | Scaffolded once by `zever new`, thereafter yours. The server template resolves a fixed battery set. Delete what you don't call. |
| `.env.example` | You | Option keys via env vars, backends via `wiring.go`, strict keys only. |
| `.github/workflows/ci.yml` | You after eject | Scaffolded once, regenerate step plus the `--check` drift gate. |

Every file under `generated/` starts with a provenance header naming the CLI release and schema revision:

```text
// Code generated by zever v0.8.0; DO NOT EDIT.
// schema-hash: sha256:9f2c…
```

`.json` specs (`openapi.json`, `mcp.json`) embed the same provenance in top-level `x-zever-generated` (`backend`, `schema`, `version`) instead. The `zever/annotations.proto` companion copy is vendored wire-stable API and is never stamped.

## Extend around generated code

Never edit `generated/`. Three patterns cover every extension point. There is deliberately no partial-file or edit-in-place mechanism, so regeneration stays a pure function of the schema:

1. **Implement the generated interface.** Each service `service.go` declares one method per RPC: implement it in your package and pass it to `Register<Service>Routes` (HTTP) and `New<Service>GRPCServer` (gRPC). Compose hand-written middleware, decorators, and wrappers around that implementation, never inside generated files.
2. **Start from a write-once stub.** `GenerateServiceStub` renders a compiling `<Service>Impl` (every method returning `Unimplemented`) for `internal/app/<module>/<service_snake>.go`. It is written once and never regenerated. The `var _ gen.Service = (*Impl)(nil)` assertion fails compilation when the interface gains methods until you add them.
3. **Embed and wrap generated types.** Generated request/response aliases and ORM models are plain Go values: embed them or convert at the boundary. For new output shapes, write a custom backend (below) instead of post-processing generated text.

Out of scope: editing generated files between runs (the next compile overwrites them, and `--check` flags the drift).

## Start small: batteries you actually need

`zever new --profile` picks adapters so prototypes skip unused batteries. `--batteries` adds to the preset, `--adapters` overrides its picks.

| Profile | Batteries | `go list -deps` packages |
|---|---|---|
| `minimal` | Bootable floor only: `log`, `router`, `auth`, `db`, `observability`, `permission`, `ratelimit` | 450 |
| `api` | Minimal plus `cache`, `queue`, `session`, `password`, `scheduler`, `outbox`, `idempotency`, `lock` | 492 |
| `full` | Every known battery | 649 |

Counts are `go list -deps ./...` package counts (stdlib plus test dependencies) for a fresh Go 1.27 scaffold at v0.6.1, measured 2026-10-13. Direct `require` lines: 22 / 38 / 82. Grow with `zever add <battery>`: three append-only edits (`go.mod`, `internal/app/wiring.go`, `.env.example`), never overwriting hand-written code.

```sh
zever new hello --profile api --dir ./hello
zever new hello --profile minimal --batteries db --adapters db=postgres
```

## Drift gate: `zever compile --check`

Teams committing `generated/` (like `examples/todo`) keep it honest with `--check`: in-memory compile, tree compare, exit 1 listing every `missing`, `differs`, or `extra` file. It writes nothing.

```sh
zever compile --check --backend=zenorm,openapi,atlas --out ./generated schema/*.zen
```

```text
zever compile: generated output differs in 2 file(s) (atlas/schema.hcl (differs), zenorm/orm/gen/app/app.go (missing)); run 'zever compile' and commit the result
```

Each file carries a provenance stamp (CLI release, schema hash). `--check` compares content and hash exactly. A stamp-version-only difference is a note listed under `stampVersionOnly` in `--json` (pass `--strict` to fail it). Run `zever compile` to refresh stamps.

Scaffolded CI (`.github/workflows/ci.yml`) regenerates from the schema then runs `--check`. If you commit `generated/`, drop the regenerate step and `--check` alone fails the build on drift. The repo's `make compile-check` (part of `make check`) runs the same gate over `examples/todo`.

<Aside type="tip">
Default scaffold gitignores `/generated/` and regenerates in CI. Commit it for reviewable DDL/API diffs, gated by `--check`.
</Aside>

## Use `orm` standalone

The typed query builder needs only a `db.DB`, never the container:

```go
import (
	"github.com/zenta-dev/zever/orm"
)

type User struct {
	ID    string
	Email string
}

var users = orm.NewTable[User]("users", []string{"id", "email"})
var colEmail = orm.NewColumn[User, string]("users", "email")

// q selects id, email from users where email = ?; no raw SQL.
q := orm.From(users).Select(colEmail).Where(colEmail.Eq("a@example.com"))
```

Dialect comes from the connection (`sqlite`/`postgres`). Unsupported features fail closed with a typed error.

## Use `core/*` standalone

Each battery is one interface plus a `New` constructor. The container is only the default resolver. Construct an adapter directly in a non-Zever program:

```go
import (
	"github.com/zenta-dev/zever/core/cache"
	memory "github.com/zenta-dev/zever/adapters/cache/memory"
)

c, err := memory.New(cache.Options{})
if err != nil {
	// ...
}
```

No globals across battery boundaries, no `init()` wiring, per-call contexts.

## Write a custom backend

`compile` is a library: implement `backend.Backend` and run it over the resolved schema from your own `main.go`. CLI `--backend` stays fixed, so custom backends ship as separate binaries, not CLI plugins.

```go
import (
	"github.com/zenta-dev/zever/dsl/backend"
	"github.com/zenta-dev/zever/dsl/compile"
	"github.com/zenta-dev/zever/dsl/ir"
)

type tsBackend struct{}

func (tsBackend) Name() string { return "ts" }

func (tsBackend) Generate(schema *ir.Schema) (map[string][]byte, error) {
	// Walk schema.Modules; return path -> content. Keep it pure:
	// no I/O here, so output stays deterministic for --check.
	return map[string][]byte{}, nil
}

func main() {
	files := map[string]string{"schema/app.zen": src}
	result, diags := compile.WithSchemaDir(files, "schema", tsBackend{})
	_ = result
	_ = diags
	_ = backend.Backend(nil)
}
```

See [Write a plugin](../write-a-plugin/) for shipping a new *adapter*. Backends are the codegen-side equivalent.

## Leaving Zever

<Steps>

1. Freeze the plumbing: run `zever compile` once and commit `generated/`.
2. Trim the entrypoints: delete unused `c.<Battery>()` calls from `cmd/server/main.go` (imports from `internal/app/wiring.go`, stanzas from `.env.example`).
3. Swap adapters in place: batteries resolve by name, so `db=sqlite` to your own store is a config plus `Register` change.
4. Drop unused framework requires (`go mod tidy` proves the build passes).
5. Keep the schema as documentation, or keep compiling: generated ORM and OpenAPI specs have no CLI runtime dependency.

</Steps>

Portable: handlers (plain `net/http`), SQL (via `orm`, dialect-explicit), committed `generated/` tree with release/schema stamps.
