`crypto` encrypts and signs payloads and fields at rest or in transit. `secrets` looks up named credentials (API keys, connection strings). They solve different problems and resolve independently. Passwords are not encrypted, see [Password hashing](../password-hashing/). For the full `secrets` service see [Secrets](../secrets/).

## Quick start

`config.Default()` ships a deterministic dev key so tests run real encryption with no setup. That key is public by construction: anything encrypted under it is recoverable by anyone who read these docs. Set a real key before deploying.

```yaml title="zever.yaml"
crypto:
  adapter: local
  options:
    key: MDEyMzQ1Njc4OTAxMjM0NTY3ODkwMTIzNDU2Nzg5MDE=   # base64, decodes to 32 bytes
secrets:
  adapter: env
  options:
    prefix: ZEVER
```

```sh
CRYPTO_KEY=prod-base64-key-here
export ZEVER_STRIPE_KEY=sk_test_example
```

```go title="main.go"
cr, err := c.Crypto()   // key missing or malformed
sec, err := c.Secrets() // prefix invalid
```

`sign_key` (optional) must decode to 64 bytes. With a real key set, resolution logs no key material and the secret `STRIPE_KEY` resolves to the exported value. Without env, `config.Default()` still resolves but uses the dev key: correct for tests, never for production. See the [crypto](../../../reference/config/#crypto) and [secrets](../../../reference/config/#secrets) config reference.

## Pick a crypto adapter

| Service | Adapter | Notes |
|---|---|---|
| `crypto` | `local` | Default. AES-256-GCM with the configured key. |
| `crypto` | `kms` | Envelope encryption (`key_id`, `key_ids`, `region`, `endpoint`, `use_envelope`). Fails closed unless you inject a real KMS client with `NewWithClient`. |
| `secrets` | `env` | Default. Reads `<PREFIX>_<NAME>` variables. |
| `secrets` | `vault` | Vault KV v2. See [Secrets](../secrets/). |

With `kms`, `key_ids` accepts prior key IDs so rotation decrypts old values while new writes use `key_id`.

## Name secrets with a prefix

The `env` adapter requires a non-empty `prefix` (default `ZEVER`). Unlike the no-prefix service env rule, secret names always carry it.

| Input | Result |
|---|---|
| `ZEVER_FOO` | Maps to secret `FOO`. |
| Empty prefix | Rejected at `Open`. |
| Slash, `..`, or spaces in prefix | Rejected at `Open`. |
| Trailing `_` | Boundary separator, added if missing. |

## Rotate the crypto key for stored fields

1. Generate the new key from a CSPRNG and inject it through env at deploy.
2. Dual-read: decrypt with the old key, re-encrypt with the new key, persist.
3. Track the old-key row count until it reaches zero.
4. Remove the old key from config and verify decrypts still succeed.

List which fields are encrypted, and under which key generation, in one place such as the migration runbook. A field nobody can name is a field nobody rotates.

## Production checklist

- Supply a real key through env or a mounted file, from a CSPRNG, kept in a secret manager.
- Resolve and audit both `crypto` and `secrets`.
- Never log raw option maps. Display config via `RedactedServices` or `Redact`. Error text names services and fields, never values.

## Troubleshooting

<details>
<summary>Production resolves but old rows decrypt to garbage</summary>

The rows were encrypted under a different key, often the dev key. Re-encrypt them under the production key during migration.
</details>

<details>
<summary>Secrets lookup misses</summary>

The env name lacks the prefix or its boundary underscore (`STRIPE_KEY` instead of `ZEVER_STRIPE_KEY`). Export the full prefixed name.
</details>

<details>
<summary>`Open` rejects the secrets prefix</summary>

The prefix is empty or contains a slash, `..`, or spaces. Use a plain alphanumeric prefix such as `ZEVER`.
</details>

<details>
<summary>Key material appears in logs</summary>

Some path logs raw options. Route all display through `RedactedServices` or `Redact` and remove the direct log call.
</details>
