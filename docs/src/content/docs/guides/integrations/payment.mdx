`payment.Payment` handles the transaction itself: create a charge, refund it, fetch it, and decode provider webhook events so you know when a payment settled. Customers and subscriptions are [Billing](../billing/). The flow is identical across `stub`, `stripe`, and `paddle`.

## Quick start

`stub` (the default) moves no money and makes no network calls. With `auto_approve: true` it marks payments `succeeded` immediately, which exercises the success path in a test without a webhook. The bookings example runs a stub charge in the booking flow.

```yaml title="zever.yaml"
payment:
  adapter: stub
  options:
    auto_approve: true
    max_webhook_bytes: 1048576
```

```sh
PAYMENT_ADAPTER=stripe
PAYMENT_SECRET_KEY=sk_live_...
PAYMENT_WEBHOOK_SECRET=whsec_...
```

Provider keys come from `shared/providersopt`: `secret_key` (Stripe), `api_key` (Paddle), `endpoint`, `sandbox`. Payment adds `webhook_secret` (signature verification, never logged, keep it in env), `auto_approve`, and `max_webhook_bytes` (default 1MiB, negative rejected). See the [payment config reference](../../../reference/config/#payment).

```go title="main.go"
package main

import (
	"context"
	"fmt"

	"github.com/zenta-dev/zever/config"
	"github.com/zenta-dev/zever/container"
	"github.com/zenta-dev/zever/core/payment"
)

func main() {
	c := container.New(config.Default())
	ctx := context.Background()
	defer c.Close(ctx)

	p, err := c.Payment()
	if err != nil {
		fmt.Println("resolve error:", err)
		return
	}
	res, err := p.CreatePayment(ctx, payment.Request{Amount: 2500, Currency: "usd"})
	if err != nil {
		fmt.Println("charge error:", err)
		return
	}
	fmt.Println("payment:", res.ID, string(res.Status))

	got, err := p.GetPayment(ctx, res.ID)
	if err != nil {
		fmt.Println("fetch error:", err)
		return
	}
	fmt.Println("fetched:", got.ID, string(got.Status))
	_ = p.Close()
}
```

Expected output with `stub` and `auto_approve: true` (IDs vary):

```text
payment: pay_01J0000000 succeeded
fetched: pay_01J0000000 succeeded
```

With `auto_approve: false` the same program prints `pending`. The webhook path flips it later.

## Verify webhooks

Webhook decoding checks the provider signature against `webhook_secret` before touching the payload, under the `max_webhook_bytes` bound. A request that fails verification or exceeds the bound never reaches your handler as a trusted `Event`. Pass the raw body unmodified to `WebhookEvent`. The default `stub` performs no webhook verification and holds no funds, so it is test-only.

## Choose an adapter

| Adapter | Package | Notes |
|---|---|---|
| `stub` | `adapters/payment/stub` | Default. No network, no real money. |
| `stripe` | `adapters/payment/stripe` | Real provider. Needs `secret_key`. |
| `paddle` | `adapters/payment/paddle` | Real provider. Needs `api_key`. |

## Production checklist

- `payment` never stores card data (the provider's PCI scope) and is not a ledger. It initiates and reacts to payments.
- `SecretKey`, `APIKey`, and `WebhookSecret` never appear in logs or errors. Hold them in [Secrets](../../security/secrets/) and use `config.RedactedServices` for display.
- Pass a refund idempotency key so a retried refund cannot double-refund.

## Troubleshooting

<details>
<summary>Stub payments stay `pending` in tests</summary>

`auto_approve` is false. Set `auto_approve: true` (or `PAYMENT_AUTO_APPROVE`) in the test config.
</details>

<details>
<summary>The webhook handler never fires</summary>

The signature check runs first. Confirm `PAYMENT_WEBHOOK_SECRET` matches the provider dashboard and the raw body reaches `WebhookEvent` unmodified.
</details>

<details>
<summary>`max_webhook_bytes` rejects large events</summary>

A provider sent a payload over the bound. Raise the bound deliberately after checking the payload is legitimate, not as a first reflex.
</details>
