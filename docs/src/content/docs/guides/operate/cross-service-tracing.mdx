## Purpose

Make one user request stay one trace across every service it touches: without propagation each service starts a fresh root trace. The convention: **extract** inbound context, **inject** outbound context, carry **baggage** for cross-cutting facts, tag every span with a **kind** and semconv attribute names.

## The propagation contract

Zever propagates W3C Trace Context (`traceparent`, `tracestate`) plus W3C Baggage, and the `otlp` adapter installs the same composite propagator (`TraceContext` + `Baggage`) as the process global:

| Boundary | What happens | Where |
|---|---|---|
| HTTP inbound | `traceparent`/`tracestate`/`baggage` extracted before the span starts | `middleware.Tracing` |
| gRPC inbound | Same three keys read from incoming metadata before the span starts | `middleware.TracingUnaryServerInterceptor` |
| HTTP outbound | Injected onto the outgoing request with `httpclient.WithTracing()` | `shared/httpclient` |
| gRPC outbound | Injected into outgoing metadata | `shared/grpcclient` interceptors |
| Queue / outbox | Stored in message headers at publish/`Record`, continued on consume | `core/outbox`, `core/job`, `traceprop.StartConsumeSpan` |

Because inbound extraction happens first, the server span is a **child** of the caller's span, not a new root.

The inbound half:

```go
import (
    "net/http"

    "github.com/zenta-dev/zever/core/middleware"
    "github.com/zenta-dev/zever/core/observability"
)

func tracedHandler(p observability.Provider, h http.Handler) http.Handler {
    // Recover outside Tracing so panics become 500s before logging sees them.
    return middleware.Tracing(p)(h)
}
```

The outbound half is a transport option, not a hand-written `RoundTripper`: pass `httpclient.WithTracing()` when building the client. The option is opt-in. The default client keeps a plain `*http.Transport`:

```go
import (
    "context"
    "net/http"
    "time"

    "github.com/zenta-dev/zever/shared/httpclient"
)

func callDownstream(ctx context.Context, url string) (*http.Response, error) {
    c := httpclient.NewClient(5*time.Second, httpclient.WithTracing())
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
    if err != nil {
        return nil, err
    }
    return c.Do(req)
}
```

Without `WithTracing()`, the client sends no `traceparent`: the downstream service starts a fresh root trace. Thread the handler's context into the request: `http.NewRequest` (no context) has no parent span to propagate. `httpclient.Inject(ctx, req)` applies headers when you already hold a request.

gRPC outbound injection needs no option: `shared/grpcclient` chains interceptors on every connection, so the context rides along. Client spans additionally need `grpcclient.WithObservability(provider)`.

Messaging has a header channel too: `Record` stores the trace context in the outbox row's headers. The relay hands those headers to the `Publisher`. Consumers holding the headers continue the trace with `traceprop.StartConsumeSpan` (`core/job`'s worker and the `eventbus` adapters already do). For send paths with no channel (mailer, SMS, push), read the ID for your logs instead of inventing protocol headers:

```go
import (
    "github.com/zenta-dev/zever/shared/traceprop"
)

// log.Println("sending receipt", traceprop.TraceID(ctx))
```

Inbound propagation is untrusted input: the OTel propagator validates
`traceparent`/`tracestate`. Invalid values are a no-op, not an error.

## Baggage

Baggage carries the facts every service in a trace needs (tenant, user, support ticket) without re-reading a header at each hop. Three keys cross a service boundary, nothing else:

| Constant | Key | Carries |
|---|---|---|
| `traceprop.BaggageTenantID` | `tenant.id` | Tenant ID for row-level filtering, per-tenant quotas |
| `traceprop.BaggageUserID` | `user.id` | User ID for audit spans |
| `traceprop.BaggageCorrelationID` | `correlation.id` | Request/job correlation ID across async work |

Set them once at the edge. Every downstream service then reads them with no plumbing. From `shared/traceprop`:

```go
// Set at the ingress handler, before any downstream call.
ctx = traceprop.WithBaggage(ctx, traceprop.BaggageTenantID, tenantID)
ctx = traceprop.WithBaggage(ctx, traceprop.BaggageUserID, userID)
ctx = traceprop.WithBaggage(ctx, traceprop.BaggageCorrelationID, correlationID)

// Read anywhere downstream; missing keys return "".
tenant := traceprop.Baggage(ctx, traceprop.BaggageTenantID)
```

Baggage copies, not shares: `WithBaggage` returns a new context, never
mutates the input. An invalid key or value leaves the context untouched.

Treat baggage as untrusted telemetry. Values ride every outbound header: keep them short, never put a secret or token there. Any value you set is visible in every downstream trace. High-cardinality values belong in span attributes or logs, not a fleet-multiplied header.

## Span kinds

A span kind tells a viewer whether the span received work or started it. `observability.StartSpan` carries the five kinds:

| Kind | Use for | Typical Zever span |
|---|---|---|
| `SpanKindServer` | Inbound request this service handles | HTTP path span, gRPC full-method span |
| `SpanKindClient` | Outbound request this service makes | `shared/grpcclient` interceptor span |
| `SpanKindProducer` | Publishing a message | Outbox publish, queue dispatch |
| `SpanKindConsumer` | Processing a received message | `traceprop.StartConsumeSpan`, `cdc` consumer |
| `SpanKindInternal` | Work inside one service | Default with no kind given |

```go
import (
    "context"

    "github.com/zenta-dev/zever/core/observability"
)

func publishSpan(ctx context.Context, t observability.Tracer, topic string) {
    ctx, span := observability.StartSpan(ctx, t, "outbox.publish",
        observability.WithSpanKind(observability.SpanKindProducer),
        observability.WithAttributes(observability.String("messaging.destination.name", topic)),
    )
    defer span.End()
}
```

`Tracer.Start(ctx, name)` exists and equals an `internal` span with no attributes. Prefer `StartSpan` when the work crosses a boundary. Providers lacking the optional `observability.SpanStarter` interface fall back to `Start`. Instrumentation never breaks an adapter.

## Provider setup

Propagation matters once spans leave the process. In production:

```sh
OBSERVABILITY_SERVICE_NAME=bookings      # keys every dashboard and alert
OBSERVABILITY_ENDPOINT=collector:4317    # host:port, no scheme or path
OBSERVABILITY_SAMPLE_RATIO=0.1
```

Give each service a distinct `OBSERVABILITY_SERVICE_NAME`: the collector draws trace boundaries from it. Keep it stable across deploys. Renaming splits a service's history in two.

Verify propagation end to end, in this order:

1. Start the collector and confirm it receives spans (`stdout` proves the instrumented code runs. Only `otlp` proves the wire).
2. Send one request through service A into service B. In the collector UI, open the trace and confirm a **single** trace ID with A's server span parenting B's. Two roots means inbound extraction is not wired.
3. Confirm an outbound call shows a client span under the server span that made it.
4. Confirm baggage: read `tenant.id` in service B. Check it matches what the edge set.

Sample early, not late: `sample_ratio: 0.1` keeps cost down. A sampled trace still carries correct parent links for recorded spans (a child whose parent was dropped renders as a new root, so a high drop rate looks like broken propagation). Verify at `sample_ratio: 1`, then lower it.

## Attribute migration (semconv)

Span and counter attribute names follow OpenTelemetry semantic conventions, so off-the-shelf dashboards and queries work against Zever traces. The migration has **shipped**. The old names are **gone** (no alias or fallback). Update saved queries, dashboards, and alert rules. `CHANGELOG.md` carries the note under `### Changed`.

| Old name (removed) | New name |
|---|---|
| `http.method` | `http.request.method` |
| `http.path` | `url.path` |
| `http.status_code` | `http.response.status_code` |
| gRPC full method as the span identity | span name still the full method, joined by `rpc.system="grpc"`, `rpc.service`, `rpc.method` attributes |
| (new) | `rpc.grpc.status_code` |
| (new) | `messaging.system`, `messaging.destination.name`, `messaging.operation`, `messaging.message.id`, `messaging.message.conversation_id` |

Query exported constants, not string literals, so a future semconv revision changes the framework instead of every query you wrote:

```go
import (
    "github.com/zenta-dev/zever/core/observability"
)

// The same keys the middleware emits, as constants.
_ = observability.HTTPRequestMethod
_ = observability.URLPath
_ = observability.HTTPResponseStatusCode
_ = observability.RPCSystem
_ = observability.RPCService
_ = observability.RPCMethod
_ = observability.RPCGRPCStatusCode
```

### Counters

Metric **names** are unchanged (the middleware still emits `http.request` and `rpc.request`). Counter **labels** migrated too. Dashboards grouping on them break silently.

| Counter | Old labels (removed) | New labels |
|---|---|---|
| `http.request` | `method` (string), `status` (status **text**, e.g. `OK`) | `http.request.method` (string), `http.response.status_code` (int) |
| `rpc.request` | `method` (full gRPC method), `outcome` (`ok` / `error`) | `rpc.service`, `rpc.method`, `rpc.grpc.status_code` (int gRPC code, `0` is `OK`) |

Two saved-query fixes: the `http.request` status label carries the numeric code, so `status="OK"` becomes `http.response.status_code=200`. The `rpc.request` counter has no `outcome` label, so success/failure grouping compares `rpc.grpc.status_code` against `0`, not `"ok"`.

Span naming stays path-only and method-only: never a query string or raw URI. The path attribute moved to `url.path` (a rename of the old HTTP path attribute, not `url.query`). Wanting the query string in a span signals logging it separately instead.

## Troubleshooting

1. Every service shows its own root trace: inbound extraction is not wired. `middleware.Tracing` must run in the handler chain (the generated server wires it), before your routes, not around each route.
2. Client calls start unrelated traces: the request context was not threaded from the handler, or the `httpclient` client lacks `httpclient.WithTracing()`. Derive the request context from `r.Context()` and set the option on `httpclient.NewClient`.
3. Baggage is empty downstream: nothing set it, or it was set after the outbound call, not at the edge. Baggage propagates forward only from the outbound call's context.
4. `go doc` shows attribute keys you do not recognize in the collector: pre-migration version. Check `CHANGELOG.md` under `### Changed` and update queries.
5. Traces stop mid-service: the provider never got a parent context, or the process uses no `otlp` adapter, so spans were dropped, not rejected. Confirm the adapter and `service_name` first.
