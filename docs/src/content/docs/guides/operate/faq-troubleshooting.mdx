## FAQ

<details>
<summary>Does Zever write my business logic?</summary>

No: it compiles `.zen` schemas into infrastructure (database access, caching, queues, routing, other batteries). Handlers, services, and rules are plain Go. See [Customizing and leaving](../../extend/customizing-and-leaving/).
</details>

<details>
<summary>How do I swap an adapter, say sqlite for postgres?</summary>

Change adapters via `zever add db/postgres`, then rebuild: `zever add` handles the `go.mod` require, wiring.go `container.Provide` entry, `.env.example` keys. The `db.DB` interface is untouched. See [Choosing batteries](../../extend/choosing-batteries/).
</details>

<details>
<summary>What is the difference between the queue, the event bus, and the outbox?</summary>

The queue is durable work for one consumer (pop, ack, retry). The event bus is live fan-out with no durability for offline handlers. The outbox records an event inside your database transaction and delivers it at least once. See [background jobs overview](../../background/overview/).
</details>

<details>
<summary>Do I need Redis?</summary>

Not to start: `memory` and `sqlite` defaults need nothing. Shared backends (Redis, `db` adapters) matter once processes share cache, queue, session, lock, rate-limit state.
</details>

<details>
<summary>Is it safe to run <code>zever tinker</code> against production?</summary>

No: `tinker` evaluates Go against a live container. Development-only, with a stderr warning. Never point it at production data.
</details>

<details>
<summary>Can I run Zever without the CLI?</summary>

Yes. Runtime packages (`config`, `container`, `core/*`, `adapters/*`) never import the compiler. The CLI scaffolds, compiles, and operates. Generated code and the runtime build with plain `go build`.
</details>

<details>
<summary>How do I turn on shell completion?</summary>

`zever completion bash|zsh|fish|powershell` prints the script. See [Shell completion](../../../reference/cli/#shell-completion-and-generated-docs). It completes `.zen` files, `generate` kinds, `--backend`, `--profile`, `--adapters`.
</details>

<details>
<summary>How do I get a heap or CPU profile from a running server?</summary>

Profile via `--pprof-addr 127.0.0.1:6060` (or `PPROF_ADDR`): off by default, loopback-only. See [Profiling with pprof](../observability/#profiling-with-pprof).
</details>

## Troubleshooting

### Configuration

<details>
<summary>Startup fails with "unknown field" or "unknown service"</summary>

The env key is close to a known field: a typo failing fast with a did-you-mean hint (`config: unknown field "MAXCONN" for service "db" (did you mean "max_conns"?)`). Check spelling against the [config reference](../../../reference/config/) and `zever config show`.
</details>

<details>
<summary>An environment variable has no effect</summary>

Env matching is ambient-safe: variables matching no field are ignored, so noise cannot break startup. Near-miss keys still fail with a did-you-mean hint (typos). Unparsable values error. Unknown service heads (`PATH`, `FOO_BAR`) and bare names (`DB`) are ignored. Set `ZEVER_CONFIG_STRICT=1` to reject every unknown key under a wired service prefix. Names follow `<SERVICE>_<FIELD>` (e.g. `DB_MAX_CONNS=20`, `AUTH_JWT_SECRET=...`), ignoring case and underscores. Layering: `defaults < .env < .env.local < process env`.
</details>

<details>
<summary>It connects to sqlite even though I configured postgres</summary>

Uppercase unprefixed env names: `DB_DSN=...` sets the connection string (backends have no env key. A `*_ADAPTER` variable fails resolution). A named instance (`DB__REPORTING__DSN`) applies to a matching Ref only, not the default `db` service.
</details>

<details>
<summary>Auth fails to open with a short or missing JWT secret</summary>

The `jwt` adapter needs a 32-byte secret. `config.Default()` ships none. Set `AUTH_JWT_SECRET`. The default dev crypto key is public and deterministic: never ship it.
</details>

### Adapters and the container

<details>
<summary>A missing backend (`NotWiredError`) at startup</summary>

The adapter's package was never imported and no `container.Provide` entry covers it. `zever add <battery>/<adapter>` wires the import and entry. The generated server validates every enabled battery at boot, reporting the missing ones with did-you-mean hints. `zever doctor` shows the same per battery.
</details>

<details>
<summary><code>zever doctor</code> reports FAIL for one battery</summary>

The battery is enabled but cannot resolve from the current config: a missing secret, an unreachable DSN, or no `container.Provide` entry in the running process. Read the error, fix the option, re-run. Doctor checks only enabled batteries.
</details>

<details>
<summary>A test leaves goroutines running</summary>

Close the container: `c.Close(ctx)` stops only resolved services, in dependency order. In tests use `t.Cleanup` or [`zevertest.NewTestContainer`](../testing-your-app/). `t.Context()` is already canceled inside cleanups, so close with a fresh bounded context.
</details>

### Schemas and codegen

<details>
<summary><code>zever compile --check</code> fails with drift</summary>

The committed output no longer matches the schema. Regenerate with `zever compile` and commit. A differing CLI version in the stamp is only a note, not drift.
</details>

<details>
<summary>The formatter refuses my file</summary>

`zever fmt` will not rewrite a file with lexical errors (e.g. an unterminated string). Fix the error. `zever check` reports it with a position.
</details>

### Background work

<details>
<summary>A dispatched job never runs</summary>

Usually a topic mismatch between the job's priority and polled topics, or a `memory` queue split across processes. See [Scheduler and jobs](../../background/scheduler-jobs/#troubleshooting).
</details>

<details>
<summary><code>Pop</code> returns an empty error</summary>

`queue.ErrEmpty` means the topic has nothing ready: handle it and poll again.
</details>

<details>
<summary>Messages are processed twice</summary>

Queues and the outbox deliver at least once. An un-acked message reappears after the visibility timeout. Make the consumer idempotent (see [idempotency](../../security/lock-idempotency/) or the outbox `Inbox`), and ack promptly.
</details>

## Still stuck?

Run `zever doctor` and `zever config show` (secrets redacted), then open an issue. Keep raw option maps out of logs and reports: print only `config.RedactedServices`.
