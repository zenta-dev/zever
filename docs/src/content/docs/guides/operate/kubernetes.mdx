Manifests for a `zever new` project: one image per entrypoint, config in a ConfigMap, secrets in a Secret, probes on `/healthz` and `/readyz`, draining shutdown. Starting point to copy and adapt. Not CLI-generated. See the [deployment checklist](../deployment/).

<Aside type="note">
Replace `registry.example.com/myapp`, the namespace, and resource numbers with your own. Assumes generated-server defaults: HTTP `8080`, gRPC `9090`, 10s shutdown grace, config from environment (`.env`).
</Aside>

## Images

`zever new` writes a multi-stage `Dockerfile` building `./cmd/server` into a distroless, non-root image. Point the builder at `./cmd/worker` for the worker (commented example ships). Tag images separately so web and worker scale independently.

```sh
docker build -t registry.example.com/myapp-server:1.0.0 \
  --build-arg VERSION=1.0.0 --build-arg REVISION="$(git rev-parse HEAD)" .
```

## Config and secrets

Keep structure in a ConfigMap, secrets in a Secret. Layering `defaults < .env < .env.local < process env`, so the Secret holds only per-environment deltas. Secrets never go in the ConfigMap or image.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: myapp-config
data:
            periodSeconds: 2
            failureThreshold: 30
          livenessProbe:
            httpGet: {path: /healthz, port: http}
            periodSeconds: 10
          readinessProbe:
            httpGet: {path: /readyz, port: http}
            periodSeconds: 5
            timeoutSeconds: 4
          lifecycle:
            preStop:
              sleep: {seconds: 5}
          resources:
            requests: {cpu: 100m, memory: 128Mi}
            limits: {memory: 256Mi}
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities: {drop: ["ALL"]}
      volumes:
        - name: config
          configMap: {name: myapp-config}
```

Why these settings:

- **Probes.** `/healthz` returns 200 with no deps: liveness and startup probe, so a down db never restarts healthy pods. `/readyz` pings the db (3s timeout) and gRPC health, returning 503 on failure. Keep the `readinessProbe` timeout above 3s.
- **Graceful shutdown.** On SIGTERM the generated server flips gRPC health to `NOT_SERVING`, calls `GracefulStop()`, shuts HTTP down, and closes the container within 10s. Keep `terminationGracePeriodSeconds` above that plus any `preStop` delay.
- **Endpoint removal races.** K8s removes a pod from Service endpoints as termination starts. Some proxies keep sending. A short `preStop` delay lets removal propagate before SIGTERM. The distroless image has no shell, so `preStop` `exec` of `sleep` is unavailable. The example uses the native `sleep` lifecycle handler (K8s 1.30+). On older clusters, add a tiny static sleep binary. Count the delay inside 30s.
- **Read-only root filesystem.** No writable path is needed unless using `local` storage or a sqlite file. Mount an `emptyDir` or volume there.
- **Config reload.** Log level and rate limiter swap on SIGHUP. Everything else needs a rollout (`kubectl rollout restart deployment/myapp-server`).

<Aside type="caution">
Do not use a `memory` cache, queue, session, lock, or rate-limit adapter with >1 replica: each pod holds its own state. Point them at Redis or your database. See [Choosing batteries](../../extend/choosing-batteries/).
</Aside>

## Service, PodDisruptionBudget, and autoscaling

```yaml
apiVersion: v1
kind: Service
metadata:
  name: myapp-server
spec:
  selector: {app: myapp, component: server}
  ports:
    - {name: http, port: 80, targetPort: http}
    - {name: grpc, port: 9090, targetPort: grpc}
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: myapp-server
spec:
  minAvailable: 2
  selector:
    matchLabels: {app: myapp, component: server}
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-server
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: myapp-server}
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: {type: Utilization, averageUtilization: 70}
```

The PodDisruptionBudget keeps two pods serving through drains. Size `minAvailable` below `minReplicas`. CPU is a reasonable first HPA signal.

## The worker Deployment

The worker runs the job worker and scheduler in one process over one shared queue, and drains the outbox relay. Give it its own Deployment and image, no Service or HTTP probes.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp-worker
spec:
  replicas: 2
  selector:
    matchLabels: {app: myapp, component: worker}
  template:
    metadata:
      labels: {app: myapp, component: worker}
    spec:
      terminationGracePeriodSeconds: 30
      securityContext:
        runAsNonRoot: true
      containers:
        - name: worker
          image: registry.example.com/myapp-worker:1.0.0
          envFrom:
            - secretRef: {name: myapp-secrets}
          volumeMounts:
          resources:
            requests: {cpu: 100m, memory: 128Mi}
            limits: {memory: 256Mi}
      volumes:
        - name: config
          configMap: {name: myapp-config}
```

Run >1 worker only with a shared queue adapter (`redis` or `db`). With >1 scheduler replica, wire a locker so a cron slot fires once, else run one scheduler replica. Scale workers on queue depth (`queue.Length`) with KEDA, not CPU. See [Scheduler and jobs](../../background/scheduler-jobs/) and the [background jobs overview](../../background/overview/).

## Migrations and one-off tasks

Run `zever db migrate` as one Kubernetes Job per release before rollout (or pipeline init step), never in every pod. A failed migration blocks rollout.

## Profiling and debugging

Generated server exposes pprof on a loopback-only listener (`--pprof-addr`). In a cluster, set `PPROF_ADDR=127.0.0.1:6060` and reach via port-forward (the loopback bind is reachable inside the pod's network namespace):

```sh
kubectl port-forward deploy/myapp-server 6060:6060
go tool pprof http://127.0.0.1:6060/debug/pprof/heap
```

See [Profiling with pprof](../observability/#profiling-with-pprof). Never run `zever tinker` against production.
