---
title: Migrate from v0.7 to v0.8
description: Move service config to environment variables, wire adapters with Provide, and run generated servers through serve.Main.
---

import { Aside, Steps, LinkCard, CardGrid } from '@astrojs/starlight/components';

v0.8 changes how a project configures and boots. Service config is environment-only, adapters wire through typed `container.Provide` calls, `zever new` scaffolds a smaller tree, and generated servers delegate boot to `serve.Main`. This page maps every change to its replacement.

**v0.8.0 is env-only: configuration moved from a config file to `.env`.**

## At a glance

| v0.7.x | v0.8.0 |
|---|---|
| `zever.yaml` (or `.yml`, `.json`, `.toml`) | `.env`, `.env.local`, or the process environment |
| `config.Load("zever.yaml")` | `config.FromEnv()` then `config.Resolve(env)` |
| `project.schema_dir` | `ZEVER_SCHEMA_DIR` |
| `project.generated_dir` | `ZEVER_GENERATED_DIR` |
| `project.server_entry` | `ZEVER_SERVER_ENTRY` |
| `project.worker_entry` | `ZEVER_WORKER_ENTRY` |
| `project.tinker_entry` | `ZEVER_TINKER_ENTRY` |
| `project.seed_entry` | `ZEVER_SEED_ENTRY` |
| `search.Postgres`, `search.SQLite` | `db` |
| `vectorstore.PGVector`, `vectorstore.SQLite` | `db` |
| `workflow.Postgres` | `db` |
| the `--config` file flag | gone from every command |

The rest of this page walks each row. Read [Check the migration](#check-the-migration) first if you want the short version: two commands tell you whether the translation is done.

## Service config is env-only

`zever.yaml`, `zever.yml`, `zever.json`, and `zever.toml` are never read. `config.Load` is gone. `config.FromEnv()` plus `config.Resolve(env)` replace them. The framework does not look for a legacy file at all: no probe, no discovery step, no warning.

<Aside type="danger" title="A leftover file is inert">
A v0.7.x file left in the working directory is silently ignored. Every service falls back to its built-in default adapter, so a half-translated project looks healthy while it talks to the wrong database. Nothing will tell you: translate the file by hand and delete it. The mapping is mechanical, `adapter:` becomes `<SERVICE>_ADAPTER` and every `options:` key becomes `<SERVICE>_<KEY>`.
</Aside>

Translate each `adapter:` and `options:` key to an uppercase env variable. Every service uses `<SERVICE>_<FIELD>`; named instances use `<SERVICE>__<NAME>__<FIELD>`.

| Service | Env prefix | Default adapter |
|---|---|---|

| analytics | `ANALYTICS_` | log |

Example:

```diff title="zever.yaml -> .env"
-db:
-  adapter: postgres
-  options:
-    dsn: postgres://app:secret@db:5432/app
-    max_conns: 20
-log:
-  adapter: slog
+DB_ADAPTER=postgres
+DB_DSN=postgres://app:secret@db:5432/app
+DB_MAX_CONNS=20
+LOG_ADAPTER=slog
```

The same project as a `.env` file, with an AI key, a JWT secret, and a named second database:

```sh title=".env"
DB_ADAPTER=postgres
DB_DSN=postgres://app:secret@db:5432/app
DB_MAX_CONNS=20
AI_ADAPTER=anthropic
AI_API_KEY=sk-...
AUTH_ADAPTER=jwt
AUTH_JWT_SECRET=prod-secret-at-least-32-bytes-long
DB__REPORTING__DSN=postgres://app:secret@db:5432/reporting
```

A named instance reaches the container only through a matching named Ref (`db.Ref("reporting")`) wired with `container.Provide`. The default instance reads the flat `<SERVICE>_<FIELD>` namespace.

Rules: `adapter:` becomes `<SERVICE>_ADAPTER`; each `options:` key becomes `<SERVICE>_<KEY>` uppercased; one nesting level flattens with a single underscore (`jwt.secret` under auth becomes `AUTH_JWT_SECRET`); durations are Go strings in env (`5s`, `1m`), not integer nanoseconds. Keys with no string form (maps, lists) cannot move to env. Full mapping and defaults: [Config reference](../../../reference/config/).

## Adapter names

Three services dropped the alias names that only existed for the old file. The DB-backed adapter has one name now, `db`, and the DSN decides the backend.

| v0.7.x alias | v0.8.0 name | Backend picked from the DSN |
|---|---|---|
| `search.Postgres` | `db` | postgres tsvector/GIN, or SQLite FTS5 |
| `search.SQLite` | `db` | postgres tsvector/GIN, or SQLite FTS5 |
| `vectorstore.PGVector` | `db` | postgres pgvector, or SQLite |
| `vectorstore.SQLite` | `db` | postgres pgvector, or SQLite |
| `workflow.Postgres` | `db` | postgres, or SQLite |

```diff title="zever.yaml -> .env"
-search:
-  adapter: postgres
-vectorstore:
-  adapter: pgvector
-workflow:
-  adapter: postgres
+SEARCH_ADAPTER=db
+VECTORSTORE_ADAPTER=db
+WORKFLOW_ADAPTER=db
```

`core/db` keeps its own two adapters: `DB_ADAPTER=sqlite` and `DB_ADAPTER=postgres` are two real databases, not aliases. A removed name does not fall back to a default. It fails with `unknown adapter`, so a stale `SEARCH_ADAPTER=postgres` stops the boot instead of quietly picking a backend you did not ask for.

## Wire adapters with Provide

The container no longer resolves adapters through name registries. `zever new` scaffolds one `Ref` var plus one `container.Provide` entry per instance, and `zever add <battery>` inserts more. Adapters still expose a `Register()` for the core registry, but the container path is `Provide`.

```diff title="internal/app/wiring.go"
-package app
-
-var DBRef = db.Ref("default")
+package app
+
+var DB = db.DefaultRef()
+var Log = log.DefaultRef()
+
+func Providers() []container.Provider {
+	return []container.Provider{
+		container.Provide(DB, dbsqlite.New),
+		container.Provide(Log, container.WrapNoErr(logslog.New)),
+	}
+}
```

Resolve through the container with `container.Get`, or keep using the accessors when the default instance is wired:

```go title="internal/app/wiring.go"
import (
	"github.com/zenta-dev/zever/container"
	"github.com/zenta-dev/zever/core/db"
)

var DB = db.DefaultRef()

// Providers wires DB to the sqlite adapter; Get(c, DB) returns the *sql.DB handle.
```

`Provide1`, `Provide2`, and `Provide3` add typed dependencies. Options come from `config.DefaultOptions` overlaid with env, then `container.WithOptions` appliers run last:

```diff title="internal/app/wiring.go"
 return []container.Provider{
-	container.Provide(DB, dbsqlite.New),
+	container.Provide(DB, dbsqlite.New, container.WithOptions(func(o *db.Options) {
+		o.MaxConns = 25
+	})),
 }
```

Graph validation runs at `container.New`: duplicate `Ref`s, missing non-`Optional` dependencies, and cycles surface from `container.Get` with typed `DuplicateRefError`, `NotWiredError`, or `DependencyCycleError`. `zever explain` prints the wiring graph. See [Container](../../../concepts/container/).

## Scaffold flags

`zever new` picks batteries with `--with`, not `--profile`. `--profile` still works as a deprecated alias that prints the equivalent `--with` form.

```diff
-zever new hello --profile api
+zever new hello --with cache,queue=redis,auth
```

`--batteries` and `--adapters` still work. `zever new` scaffolds the minimal tree (about eight files): `go.mod`, `schema/app.zen`, `cmd/server/main.go`, `internal/app/wiring.go`, `internal/service/hello`, `.env`, `.env.example`, and `.gitignore`. Recipes such as `docker`, `ci`, `worker`, `seed`, `compose`, and `k8s` are opt-in via `zever add <recipe>`.

## Generated servers use serve.Main

The generated `cmd/server/main.go` is thin. It parses `-addr` and `-grpc-addr`, then calls `serve.Main` with the app's providers and modules. `serve.Main` owns config resolution, container construction, signal handling, and graceful shutdown.

```diff title="cmd/server/main.go"
-func main() {
-	// build container, resolve router, start http.Server, wait for signal
-}
+func main() {
+	addr := flag.String("addr", "", "HTTP listen address (empty uses PORT, default :8080)")
+	grpcAddr := flag.String("grpc-addr", "", "gRPC listen address (empty disables)")
+	flag.Parse()
+
+	var opts []serve.Option
+	if port, err := serverPort(*addr); err == nil && port != "" {
+		opts = append(opts, serve.WithPort(port))
+	}
+	if *grpcAddr != "" {
+		opts = append(opts, serve.WithGRPCAddr(*grpcAddr))
+	}
+
+	if err := serve.Main(app.Providers(), app.Modules(), opts...); err != nil {
+		fmt.Fprintln(os.Stderr, "server:", err)
+		os.Exit(1)
+	}
+}
```

Listen addresses and runtime toggles come from env or options: `PORT` (default `8080`), `GRPC_ADDR` (empty disables gRPC), `PPROF_ADDR` (loopback pprof, empty disables), `GRPC_REFLECTION`, and `ZEVER_ENV`. Security defaults stay fail-closed: reflection off unless opted in, TLS 1.2 floor, security headers, and refusal of the deterministic dev crypto key outside a dev `ZEVER_ENV`. See [Serve module](https://github.com/zenta-dev/zever/tree/main/serve).

## CLI surface

- `worker` and `schedule run` are the canonical commands. `queue:work` and `schedule:run` still work as hidden aliases.
- `doctor` scopes its report to wired providers; it no longer takes `--config`.
- `config show` prints per-instance redacted values and no longer takes `--config`.
- `zever explain` prints the wiring graph when invoked bare, or one service's wiring for `zever explain db` / `zever explain db/analytics`.
- `zever add <battery>/<adapter>` edits `internal/app/wiring.go` with `go/ast`, appends to `.env.example`, and runs `go get` plus `go mod tidy`.

## Project layout settings

Project layout is defaults-only, overridable by six `ZEVER_*` variables (no file, no `--config` flag). The v0.7.x `project` stanza moved key by key:

| v0.7.x file key | v0.8.0 env variable | Overrides | Default |
|---|---|---|---|
| `project.schema_dir` | `ZEVER_SCHEMA_DIR` | `.zen` schema directory | `schema` |
| `project.generated_dir` | `ZEVER_GENERATED_DIR` | generated-code directory | `generated` |
| `project.server_entry` | `ZEVER_SERVER_ENTRY` | server entrypoint package | `cmd/server` |
| `project.worker_entry` | `ZEVER_WORKER_ENTRY` | worker entrypoint package | `cmd/worker` |
| `project.tinker_entry` | `ZEVER_TINKER_ENTRY` | tinker shim entrypoint | `cmd/tinker-shim` |
| `project.seed_entry` | `ZEVER_SEED_ENTRY` | seed entrypoint package | `db/seed` |

## Check the migration

<Steps>
1. Read the resolved values back. `zever config show` prints one `<service>  adapter=<x>` header per service with its redacted options, and one `<service>/<NAME>` section per named instance. Compare it with the file you translated: every service you configured must show the adapter and the option values you moved over.

   ```sh
   zever config show
   ```

2. Resolve every wired battery. `zever doctor` checks each one and exits non-zero when a check fails, so it gates a pre-deploy pipeline.

   ```sh
   zever doctor
   ```
</Steps>

A wrong value is loud, so those two commands are enough:

| What is wrong | What you see |
|---|---|
| A removed adapter alias, for example `SEARCH_ADAPTER=postgres` | `search  FAIL  container: search: search: unknown adapter: postgres (forgotten import?)` |
| A misspelled key, for example `DB_MAXCONN=20` | `config: unknown field "MAXCONN" for service "db" (did you mean "max_conns"?)`, then `check env key "DB_MAXCONN" (did you mean "DB_MAX_CONNS"?)` |
| A value that does not parse, for example `DB_MAX_CONNS=abc` | `config: invalid options db: config: invalid value for field "MAX_CONNS" from env DB_MAX_CONNS: expected int` |
| A v0.7.x file still in the working directory | nothing at all: the file is never read, so every service falls back to its built-in default adapter |

That last row is the only silent one. A leftover file never fails a check, so compare `zever config show` against the file you translated, then delete the file.

## Migration checklist

1. Move every `zever.yaml` stanza to `.env` or the process environment using the table above.
2. Rename the removed adapter aliases to `db` for the `search`, `vectorstore`, and `workflow` services.
3. Move the `project` stanza to the `ZEVER_*` variables.
4. Delete `zever.yaml`; nothing reads it, so a leftover file is ignored and its values are lost.
5. Replace `config.Load(...)` with `config.FromEnv()` plus `config.Resolve(env)`.
6. Replace adapter `Register()` wiring with `container.Provide` entries in `internal/app/wiring.go`.
7. Replace `--profile` with `--with` in scripts and CI.
8. Regenerate the server entrypoint so it calls `serve.Main` with providers and modules.
9. Update Kubernetes manifests to inject `env:` from a Secret (no mounted config file).
10. Run `zever config show` and `zever doctor`, and compare the output with the values you moved over.
