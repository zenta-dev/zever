---
title: Migrate from v0.7 to v0.8
description: Move service config to environment variables, wire adapters with Provide, and run generated servers through serve.Main.
---

import { Aside, Steps, LinkCard, CardGrid } from '@astrojs/starlight/components';

v0.8 makes service config environment-only, wires adapters through typed `container.Provide` calls, delegates generated-server boot to `serve.Main`.

## At a glance

| v0.7.x | v0.8.0 |
|---|---|
| `zever.yaml` (or `.yml`, `.json`, `.toml`) | `.env`, `.env.local`, process environment |
| `config.Load("zever.yaml")` | `config.FromEnv()` then `config.Resolve(env)` |
| `project.schema_dir` | `ZEVER_SCHEMA_DIR` |
| `project.generated_dir` | `ZEVER_GENERATED_DIR` |
| `project.server_entry` | `ZEVER_SERVER_ENTRY` |
| `project.worker_entry` | `ZEVER_WORKER_ENTRY` |
| `project.tinker_entry` | `ZEVER_TINKER_ENTRY` |
| `project.seed_entry` | `ZEVER_SEED_ENTRY` |
| `search.Postgres`, `search.SQLite` | `db` |
| `vectorstore.PGVector`, `vectorstore.SQLite` | `db` |
| `workflow.Postgres` | `db` |
| `--config` file flag | gone from every command |

Two commands verify the translation: [Check the migration](#check-the-migration).

## Service config is env-only

`zever.yaml`, `zever.yml`, `zever.json`, and `zever.toml` are never read. `config.Load` is gone. `config.FromEnv()` plus `config.Resolve(env)` replace it: no probe, discovery, or warning.

<Aside type="danger" title="A leftover file is inert">
A leftover v0.7.x file is silently ignored: every service falls back to compiled-in wiring, so a half-translated project looks healthy while talking to the wrong database. Translate it by hand and delete it: every `options:` key becomes `<SERVICE>_<KEY>`, each `adapter:` a `container.Provide` entry (plus import) in `internal/app/wiring.go`.
</Aside>

Translate each `adapter:`/`options:` key to uppercase env: `<SERVICE>_<FIELD>`, named instances `<SERVICE>__<NAME>__<FIELD>`.

```diff title="zever.yaml -> .env"
-db:
-  adapter: postgres
-  options:
-    dsn: postgres://app:secret@db:5432/app
-    max_conns: 20
-log:
-  adapter: slog
+DB_DSN=postgres://app:secret@db:5432/app
+DB_MAX_CONNS=20
```

```sh title=".env"
DB_DSN=postgres://app:secret@db:5432/app
DB_MAX_CONNS=20
AI_API_KEY=sk-...
AUTH_JWT_SECRET=prod-secret-at-least-32-bytes-long
DB__REPORTING__DSN=postgres://app:secret@db:5432/reporting
```

Named instances reach the container only through a matching `container.Provide`-wired Ref (`db.Ref("reporting")`).

`adapter:` becomes a `container.Provide` entry in `internal/app/wiring.go` (no adapter env key. Any `*_ADAPTER` key fails resolution), each `options:` key becomes `<SERVICE>_<KEY>` uppercased, one nesting level flattens with a single underscore (`jwt.secret` becomes `AUTH_JWT_SECRET`), durations are Go strings in env (`5s`, `1m`). Keys with no string form (maps, lists) cannot move to env. See [Config reference](../../../reference/config/).

## Adapter names

Three services dropped file-only alias names. One DB-backed constructor now (`searchdb.New` and friends). The DSN picks the backend: postgres URL selects postgres, anything else embedded sqlite.

| v0.7.x alias | v0.8.0 name | Backend picked from the DSN |
|---|---|---|
| `search.Postgres` | `db` | postgres tsvector/GIN, or SQLite FTS5 |
| `search.SQLite` | `db` | postgres tsvector/GIN, or SQLite FTS5 |
| `vectorstore.PGVector` | `db` | postgres pgvector, or SQLite |
| `vectorstore.SQLite` | `db` | postgres pgvector, or SQLite |
| `workflow.Postgres` | `db` | postgres, or SQLite |

```diff title="zever.yaml -> .env"
-search:
-  adapter: postgres
-vectorstore:
-  adapter: pgvector
-workflow:
-  adapter: postgres
(no env change: the same `db` constructor reads the DSN and picks the backend)
```

`core/db` keeps two real databases behind two constructors (`dbsqlite.New`, `dbpostgres.New`): switching is an import plus a `container.Provide` change. Removed backends never fall back to a default. A stale `*_ADAPTER` key fails resolution instead of quietly picking an unasked backend.

## Wire adapters with Provide

No name registries: `zever new` scaffolds one `Ref` var plus one `container.Provide` entry per instance. `zever add <battery>` inserts more. Adapters expose only a `New` constructor. The container path is `Provide`.

```diff title="internal/app/wiring.go"
-package app
-
-var DBRef = db.Ref("default")
+package app
+
+var DB = db.DefaultRef()
+var Log = log.DefaultRef()
+
+func Providers() []container.Provider {
+	return []container.Provider{
+		container.Provide(DB, dbsqlite.New),
+		container.Provide(Log, container.WrapNoErr(logslog.New)),
+	}
+}
```

Resolve with `container.Get`, or keep accessors when the default instance is wired:

```go title="internal/app/wiring.go"
import (
    "github.com/zenta-dev/zever/container"
    "github.com/zenta-dev/zever/core/db"
)

var DB = db.DefaultRef()

// Providers wires DB to the sqlite adapter; Get(c, DB) returns the *sql.DB handle.
```

`Provide1`, `Provide2`, `Provide3` add typed dependencies. Options come from `config.DefaultOptions` overlaid with env. `container.WithOptions` appliers run last:

```diff title="internal/app/wiring.go"
 return []container.Provider{
-	container.Provide(DB, dbsqlite.New),
+	container.Provide(DB, dbsqlite.New, container.WithOptions(func(o *db.Options) {
+		o.MaxConns = 25
+	})),
 }
```

At `container.New`, duplicate `Ref`s, missing non-`Optional` dependencies, and cycles surface from `container.Get` as `DuplicateRefError`, `NotWiredError`, or `DependencyCycleError`. Print the graph with `zever explain`. See [Container](../../../concepts/container/).

## Scaffold flags

`zever new` picks batteries with `--with`, not `--profile`. `--profile` remains a deprecated alias printing the equivalent `--with` form.

```diff
-zever new hello --profile api
+zever new hello --with cache,queue=redis,auth
```

`--batteries` and `--adapters` still work. `zever new` scaffolds the tree (about eight files): `go.mod`, `schema/app.zen`, `cmd/server/main.go`, `internal/app/wiring.go`, `internal/service/hello`, `.env`, `.env.example`, `.gitignore`. Recipes (`docker`, `ci`, `worker`, `seed`, `compose`, `k8s`) are opt-in via `zever add <recipe>`.

## Generated servers use serve.Main

The generated `cmd/server/main.go` is thin: it parses `-addr` and `-grpc-addr`, then calls `serve.Main` with the app's providers and modules, which owns config resolution, container construction, signal handling, and graceful shutdown.

```diff title="cmd/server/main.go"
-func main() {
-	// build container, resolve router, start http.Server, wait for signal
-}
+func main() {
+	addr := flag.String("addr", "", "HTTP listen address (empty uses PORT, default :8080)")
+	grpcAddr := flag.String("grpc-addr", "", "gRPC listen address (empty disables)")
+	flag.Parse()
+
+	var opts []serve.Option
+	if port, err := serverPort(*addr); err == nil && port != "" {
+		opts = append(opts, serve.WithPort(port))
+	}
+	if *grpcAddr != "" {
+		opts = append(opts, serve.WithGRPCAddr(*grpcAddr))
+	}
+
+	if err := serve.Main(app.Providers(), app.Modules(), opts...); err != nil {
+		fmt.Fprintln(os.Stderr, "server:", err)
+		os.Exit(1)
+	}
+}
```

Listen addresses come from env or options: `PORT` (default `8080`), `GRPC_ADDR` (empty disables gRPC), `PPROF_ADDR` (loopback pprof, empty disables), `GRPC_REFLECTION`, `ZEVER_ENV`. Security defaults stay fail-closed: opt-in reflection, TLS 1.2 floor, security headers, no dev crypto key outside a dev `ZEVER_ENV`. See [Serve module](https://github.com/zenta-dev/zever/tree/main/serve).

## CLI surface

- `worker` and `schedule run` are canonical. `queue:work` and `schedule:run` remain hidden aliases.
- `doctor` scopes its report to wired providers (no `--config`).
- `config show` prints per-instance redacted values (no `--config`).
- `zever explain` prints the wiring graph bare, or one service's wiring for `zever explain db` / `zever explain db/analytics`.
- `zever add <battery>/<adapter>` edits `internal/app/wiring.go` via `go/ast`, appends to `.env.example`, runs `go get` plus `go mod tidy`.

## Project layout settings

Project layout is defaults-only, overridable by six `ZEVER_*` variables (no file, no `--config` flag):

| v0.7.x key | v0.8.0 variable | Overrides | Default |
|---|---|---|---|
| `project.schema_dir` | `ZEVER_SCHEMA_DIR` | schema dir | `schema` |
| `project.generated_dir` | `ZEVER_GENERATED_DIR` | generated dir | `generated` |
| `project.server_entry` | `ZEVER_SERVER_ENTRY` | server entrypoint | `cmd/server` |
| `project.worker_entry` | `ZEVER_WORKER_ENTRY` | worker entrypoint | `cmd/worker` |
| `project.tinker_entry` | `ZEVER_TINKER_ENTRY` | tinker shim entrypoint | `cmd/tinker-shim` |
| `project.seed_entry` | `ZEVER_SEED_ENTRY` | seed entrypoint | `db/seed` |

## Check the migration

<Steps>
1. Read the resolved values: `zever config show` prints one `<service>  driver=<x>` header per service with redacted options, plus one `<service>/<NAME>` section per named instance. Every configured service must show the wired driver and the moved-over values.

   ```sh
   zever config show
   ```

2. Resolve every wired battery: `zever doctor` exits non-zero on failure, so it gates a pre-deploy pipeline.

   ```sh
   zever doctor
   ```
</Steps>

A wrong value is loud:

| What is wrong | What you see |
|---|---|
| A stale adapter key (e.g. a removed `SEARCH_ADAPTER` variable) | `config: unknown field "ADAPTER" for service "search": adapter selection removed; wire in internal/app/wiring.go with container.Provide and rebuild` |
| A misspelled key, e.g. `DB_MAXCONN=20` | `config: unknown field "MAXCONN" for service "db" (did you mean "max_conns"?)`, then `check env key "DB_MAXCONN" (did you mean "DB_MAX_CONNS"?)` |
| An unparsable value, e.g. `DB_MAX_CONNS=abc` | `config: invalid options db: config: invalid value for field "MAX_CONNS" from env DB_MAX_CONNS: expected int` |
| A leftover v0.7.x file in the working directory | nothing at all: the file is never read, so every service falls back to its compiled-in wiring |

Only the last row is silent: a leftover file never fails a check, so compare and delete.

## Migration checklist

1. Move every `zever.yaml` stanza to `.env` or process env (table above).
2. Point `search`, `vectorstore`, `workflow` at the `db` constructors (`searchdb.New` and friends pick the backend from the DSN).
3. Move the `project` stanza to `ZEVER_*`.
4. Delete `zever.yaml`: unread, a leftover is ignored and its values are lost.
5. Replace `config.Load(...)` with `config.FromEnv()` plus `config.Resolve(env)`.
6. Replace adapter `Register()` wiring with `container.Provide` entries plus imports in `internal/app/wiring.go`.
7. Replace `--profile` with `--with` everywhere.
8. Regenerate the server entrypoint around `serve.Main` with providers and modules.
9. Update Kubernetes manifests to inject `env:` from a Secret.
10. Run `zever config show` and `zever doctor`. Compare against the moved-over values.
