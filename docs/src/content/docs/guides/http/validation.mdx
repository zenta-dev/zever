Validation lives in two places: declarative `@validate` rules in `.zen` (shape and format) and explicit Go checks in handlers (transport and business rules). Both fail with field-named errors, never silent coercion. There is no config block, no adapter, and no container accessor.

## Quick start

Declare shape rules in the schema (syntax: [Zen syntax](../../../reference/zen-syntax/)):

```zen
rpc CreateUser(email: string @validate(format: "email")) -> User {
  http: POST "/v1/users"
  auth: required
  errors: { already_exists }
}

field title: string @validate(min_len: 1, max_len: 200)
```

The resolver checks each expression at compile time, and `zever check` reports bad rules with positions. `@validate` travels into generated code and OpenAPI, so docs, server, and client agree.

Then check the rest in the handler, in strict order: parse, validate, then call `db`, `queue`, or payment. Failed validation must never open a transaction or cause a side effect.

```go title="handlers.go"
func createUser(w http.ResponseWriter, r *http.Request) {
    var in struct {
        Email string `json:"email"`
        Name  string `json:"name"`
    }
    if err := json.NewDecoder(r.Body).Decode(&in); err != nil {
        writeError(w, http.StatusBadRequest, "invalid body")
        return
    }
    if !strings.Contains(in.Email, "@") {
        writeError(w, http.StatusUnprocessableEntity, "email: must be a valid address")
        return
    }
    if strings.TrimSpace(in.Name) == "" {
        writeError(w, http.StatusUnprocessableEntity, "name: required")
        return
    }
    writeJSON(w, http.StatusCreated, map[string]string{"email": in.Email})
}
```

```sh
curl -s -X POST localhost:8080/v1/users -d '{"email":"a@example.com","name":"Ada"}'
curl -s -X POST localhost:8080/v1/users -d '{"email":"nope","name":"Ada"}'
curl -s -X POST localhost:8080/v1/users -d 'not json'
```

```text
{"email":"a@example.com"}
{"error":"email: must be a valid address"}
{"error":"invalid body"}
```

`writeJSON` and `writeError` are the app helpers from [Requests and responses](../requests-responses/).

| Status | When |
|---|---|
| `400` | Malformed body or query (cannot parse). |
| `422` | Well-formed but invalid (bad email, empty name). |
| `409` | `already_exists`, from the RPC `errors:` set. |

## Split rules between schema and handler

Give each rule one owner so behavior never depends on which layer runs first.

| Rule kind | Owner | Example |
|---|---|---|
| Shape and format | `.zen` `@validate` | `email` format, `title` length bounds |
| Transport integrity | Handler | JSON parses, required headers present |
| Business state | Handler plus store | Email not already registered (409) |
| Config sanity | Startup `Validate` | Adapter options, DSN present |

Bookings puts format rules on entities (`User.email`, `Space.title`) and flow rules in `internal/api` (guest phone, idempotency key, flag-gated checkout). Generated OpenAPI reflects only the schema half, so document handler rules in endpoint notes.

```go
// Flow rule: feature-flag gate (fl is the resolved core/flag Flag).
if ok, _ := fl.Bool(ctx, "checkout", false); !ok {
    writeError(w, http.StatusNotFound, "checkout disabled")
    return
}
// Store rule: ErrConflict is an app-owned sentinel from your store layer.
if errors.Is(err, ErrConflict) {
    writeError(w, http.StatusConflict, "already exists")
    return
}
```

## Validate config at startup

Adapter options validate the same way. `config.Load(path)` decodes strictly, so unknown file fields fail fast. An unparsable env value returns `InvalidOptionsError` (for example `DB_MAXCONNS=abc`) naming the service and field, never the secret. Unknown env vars are ignored, so a stray `AUTH_TOKEN` cannot break boot.

## Production checklist

- Name the field and the rule in messages, never the rejected secret value.
- Keep validation before I/O so it needs no deadline and leaves nothing to drain on `c.Close(ctx)`.
- Treat RPC error-set changes as API changes: `breaking` flags them, so note new variants in release docs.

## Troubleshooting

<details>
<summary>`zever check` rejects a rule the handler accepts</summary>

The schema expression has a typo or unsupported constraint. Fix the `.zen` source; the resolver is the authority.
</details>

<details>
<summary>Clients get 400 for business errors</summary>

The handler conflates parse failure with rule failure. Return 400 only for unparsable bodies, 422 for well-formed invalid values.
</details>

<details>
<summary>409 never fires on duplicates</summary>

The RPC lacks `errors: { already_exists }`, or the handler does not map the conflict. Declare the set and translate the store conflict to 409.
</details>

<details>
<summary>Boot fails on a config typo</summary>

Strict decoding rejects unknown fields. Use the snake_case key (`max_conns`, not `maxconns`). Env names ignore case and `_`.
</details>

<details>
<summary>Tests pass bad emails</summary>

Assertions check status only. Table-drive the boundary (valid, no at-sign, empty) and assert status plus message.
</details>
