Working result fast, then deeper. Rules for adding or editing pages.

## Choose the page type first

One page, one job. Mixing jobs confuses.

| Type | Reader's question | Lives in | Tone |
|---|---|---|---|
| Tutorial | "Teach me." | `tutorials/`, `start/quickstart` | Encouraging, linear |
| How-to guide | "Help me do X." | `guides/` | Direct, task-first |
| Concept | "Help me understand." | `concepts/` | Explains why |
| Reference | "Tell me the exact fact." | `reference/` | Neutral, scannable |

Split two-job pages, link the halves.

## Voice and style

- Write to "you", present tense, active voice.
- Condition before instruction: "If you use Redis, set `cache.adapter`."
- Sentences near 20 words, paragraphs 4 lines or fewer.
- Use plain words. Cut "simply", "just", "easily", "note that", and "in order to".
- Sentence case for headings. Name the task in guides ("Cache a value with a TTL").
- Keep every H2 self-contained: name the subject, never "as above".
- Numbered lists for steps, bullets for unordered items, tables for comparisons.
- Code, file names, flags, and config keys in code font. UI labels in bold.
- Link text names the destination. Never write "click here".
- Say "Zever" in prose, lowercase `zever` only in code, commands, paths, URLs.
- No em or en dashes. Use a comma, colon, period, or parentheses.

## Avoid AI writing patterns

- No em or en dashes (see Voice and style).
- No bold-prefix bullets (`**Feature:** description`). Use plain bullets or a table.
- No semicolons as separators. Use a comma or split it.
- No formulaic transitions: "In this section", "As mentioned above", "It is important to note", "Let's dive in".
- No buzzwords: "robust", "seamless", "comprehensive", "streamline", "unlock", "empower", "delve", "leverage", "elevate".
- No filler: "simply", "just", "easily", "note that", "in order to", "basically", "actually", "of course", "obviously".
- No `--` disguised as a dash.
- No staccato fragment rhythm manufactured for effect.

## Show code that works

- Snippets run as written. Include imports (`github.com/zenta-dev/zever/...`) and expected output.
- Name the file in the block title: ` ```go title="main.go" `.
- Mark complete `package main` snippets with `check`: ` ```go title="main.go" check `. CI (`tools/check-doc-snippets.sh`) compiles and vets marked blocks in a temp module joined to the workspace, so renamed fields or removed functions fail the build. Fragments (unmarked blocks): CI checks `github.com/zenta-dev/zever/...` imports resolve and each `pkg.Symbol` exists. Run `tools/check-doc-snippets.sh` before pushing.
- Verify config keys against the Go `Options` structs (`core/<service>/options.go` and `adapters/<service>/<adapter>/options.go`). No generated schema: config is env-only. Field names are Go snake_case (`max_conns`). Environment variables are `<SERVICE>_<FIELD>` with no prefix (`DB_MAX_CONNS`). A named instance is `<SERVICE>__<NAME>__<FIELD>`.
- The default instance is flat `<SERVICE>_<FIELD>`. `<SERVICE>__DEFAULT__<FIELD>` is a NAMED instance called `DEFAULT` that no container wiring resolves. Never write it. CI (`docs/scripts/audit-facts.mjs`) fails that spelling, unknown config services, and adapter names the service lacks.
- Verify commands and flags against `cmd/zever`. Never invent one.
- Keep guide snippets minimal, with full option lists in [Config reference](../../reference/config/) under its `#service` anchor.
- Port docs-missing detail from package `README.md` files.

## Keep it short without losing facts

- Answer first: what it is, when to use it, in two sentences or fewer.
- Cut backstory, repetition, marketing. Keep facts, keys, failure cases.
- Move rare detail into `<details>` blocks or reference tables.
- At most two callouts (`Aside`) per page. An always-true callout belongs in the body.
- Link instead of re-explaining. Each fact has one home.

## Templates

### Tutorial

```md
---
title: Build a booking API
description: Build and run a bookings API from an empty folder.
---

You will build X. It takes about N minutes. You need Go 1.27+ and Zever installed.

## Create the project
1. Run `zever new ...`  (then show the expected output)

## Define the schema
...

## Run it
...

## What you built
Two or three lines, then next steps (LinkCards).
```

### How-to guide (one per battery or task)

```md
---
title: Cache
description: Cache values with a TTL, in memory or in Redis.
---

One or two sentences: what it is and when to use it.

## Quick start
Minimal config, minimal code, expected output.

## Cache a value with a TTL        <- task sections, 2 to 5 of them
## Share the cache across instances
## Choose an adapter                <- small table, link to the adapters matrix
## Production checklist             <- short bullets
## Troubleshooting                  <- symptom, cause, fix, in <details>
## Related                          <- LinkCards
```

### Concept

```md
One-line summary.

## The mental model        (diagram or table)
## How it works
## Design decisions and trade-offs
## Related
```

### Reference

```md
One-line summary.

## <Service or command>    <- stable anchor, identical table layout on every entry
| Key | Type | Default | Description |
```

## Frontmatter

- `title`: page name in sentence case, under 60 characters.
- `description`: one sentence under 160 characters. Start guides with a verb ("Cache values with a TTL").
- `sidebar.label`: only when the nav needs a shorter name.

## Before you open a pull request

1. Run `npm run build` in `docs/`, fix your warnings.
2. Run `npm run check-links` in `docs/` (reads `docs/dist`): zero broken targets.
3. Run `npm run lint` in `docs/`: errors on dashes, lowercase brand in prose, missing or long description, over two callouts. Warns on title-cased headings.
4. Run `npm run audit` in `docs/`: cross-checks env keys, instance namespace, adapter names, container accessors, CLI commands and flags, import paths against code, ending with 0 problems. CI runs it per PR. A page disagreeing with code fails the build.
5. Run `npm run check-legacy-config` in `docs/`. Fails on `zever.yaml`-style files, unnamed service "config files". Config is env-only since v0.8.0. Such files are inert, values drop in silence. Name it only to say it is never read, or in migration. Non-service files (policy doc, TLS cert, secret token file, Kubernetes manifest) pass. Whole-repo scan (root markdown, modules, examples, editor READMEs, scripts, Go source). A `core/db/README.md` mention fails like a page mention.
6. De-AI pass as style guidance, not a CI gate: avoid em or en dashes, bold-prefix bullets, formulaic transitions, buzzwords, and filler. Only the `npm run lint` findings in step 3 fail the build.
7. Add a `CHANGELOG.md` entry under `[Unreleased]` for user-facing changes.

Steps 1 to 5 gate CI: the `docs` workflow and the `docs-audit` job of the `ci` workflow fail the PR on any problem. Self-tests (`npm run lint:self-test`, `npm run check-links:self-test`, `npm run check-legacy-config:self-test`) prove each checker bites. `make docs-gates` runs the set locally.

External (http) links rot and need the network, so lychee reports instead of gating.
