---
title: Secrets
description: Named secret storage, separate from layered config.
---

`config` answers "what value does this field have" — defaults, then a file,
then environment overrides, all fine to see in a diff. `secrets` answers a
narrower question: "give me this one named credential, on demand, without it
ever sitting in a YAML file or scrolling past in a log line." They're
deliberately separate services, not two halves of the same one.

`secrets.Options` is already shaped for a Vault backend (`Addr`, `Token`,
`Mount`), GCP Secret Manager (`ProjectID`), and AWS (`Region`) — but today only
one adapter ships: `env`, which reads `<PREFIX>_<NAME>` environment variables
directly. The unused fields aren't dead weight; they're the seam a future
backend plugs into without a breaking change to `Options`.

## Config

```yaml
secrets:
  adapter: env
  options:
    prefix: ZEVER
```

```sh
SECRETS_PREFIX=ZEVER
```

## Resolve

```go
c := container.New(config.Default())
s, err := c.Secrets()
if err != nil {
	// handle
}
_ = s
```

`Secrets()` resolves lazily like every other accessor; `Close(ctx)` takes a
context, unlike most services in this table.

## Adapters

| Adapter | Package | Notes |
|---|---|---|
| `env` | `secrets/env` | Only adapter shipped today; reads `<PREFIX>_<NAME>` |

## The gotcha: `env` is read-only

Calling `Set` or `Delete` against the `env` adapter always returns
`secrets.ErrNotSupported` — it can't write back to the process environment, so
it doesn't pretend to. If your app needs to rotate or write secrets at runtime
rather than just read them at startup, the shipped adapter isn't where that
lands; a Vault or cloud secrets-manager adapter would need to exist first, and
`Options`' unused fields are exactly where it would slot in.

`ValidateName` rejects names containing `/` or `..`, so a secret name can never
be used for path traversal against a backend that stores secrets hierarchically
(a Vault KV mount, for instance) — even though `env` itself has no such
hierarchy to traverse. Values never appear in errors; only the service and
field name do, same redaction discipline as `config.RedactedServices`.
