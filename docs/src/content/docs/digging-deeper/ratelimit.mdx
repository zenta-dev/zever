---
title: Rate Limiting
description: Token-bucket limits in memory or shared over Redis.
---

An endpoint with no rate limit is one abusive client away from taking down
everyone else's experience. `ratelimit.Limiter` gives you a token-bucket
`Allow` check per key that returns a `Decision` — `Allowed`, `RetryAfter`,
`Remaining` — and stays deliberately unopinionated about HTTP: mapping a denial
to a `429` and choosing fail-open-vs-fail-closed on limiter error is on you.

`memory` (the default) is fine while you run one instance — a token bucket that
only your process can see is still a real limit. The moment you run more than
one replica behind a load balancer, a per-instance bucket means your effective
limit is `limit × replica count`, which is rarely what you meant; switch to
`redis` so every replica shares the same counters.

## Config

```yaml
ratelimit:
  adapter: memory
  options:
    rate: 10
    burst: 20
```

```sh
RATELIMIT_ADAPTER=redis
RATELIMIT_RATE=100
```

## Resolve

```go
c := container.New(config.Default())
rl, err := c.Ratelimit()
if err != nil {
	// handle
}
_ = rl
```

## Adapters

| Adapter | Package | Notes |
|---|---|---|
| `memory` | `ratelimit/memory` | Default; process-local |
| `redis` | `ratelimit/redis` | Shared counters |

## The gotcha: choose fail-open vs. fail-closed deliberately, per path

`ratelimit` doesn't decide this for you — a limiter error on a login endpoint
should probably fail closed (deny) since that's an auth-adjacent path where
"just let it through" is the riskier default; a limiter error on a
non-critical read path can reasonably fail open so a Redis blip doesn't take
your whole API down. Keys are capped at 256 bytes with no control bytes
(`InvalidKeyError` reports only the length, since keys — an IP, a user ID — can
be PII), and charges cap at the bucket's burst size, so a single oversized
request can't silently drain more budget than the bucket actually holds.
