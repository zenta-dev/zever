title: Outbox
description: Transactional outbox/inbox: events that commit with the business row, delivered at-least-once.

## Purpose

Use `outbox` to fix the dual-write hazard. A booking row and its
`booking.created` event are two writes; without coordination the row can
commit while the event is lost (process crash, broker down, bug between
the two writes). `Store.Record(ctx, tx, msg)` persists the message inside
the caller's transaction — the same `db.Tx` as the business write — so
either both commit or neither does. A relay then publishes the stored
message with at-least-once delivery, and `Inbox` makes consumers
idempotent by recording each event ID in the same transaction as the side
effect.

## When to use

Use the outbox whenever an event must not be lost when a row is written:
domain events for downstream services, webhook fan-out, cache
invalidation, audit trails. Pick `db` (the default) for anything durable:
sqlite for dev, postgres for prod. Pick `memory` for tests and demos —
it publishes synchronously and keeps nothing. Pick `cdc` when postgres is
the system of record and you want the WAL itself as the relay transport,
without a polling loop.

Do not use the outbox for work that must happen exactly once. Delivery is
at-least-once; pair it with the `Inbox` (or your own idempotency key) on
the consumer side. Core stays transport-agnostic: it never imports
`eventbus` or `queue`. Application wiring bridges a concrete transport to
the `Publisher` interface — the `Options.Publisher` string (`"eventbus"`,
`"queue"`, or `""`) records which transport you wired; it is informational
only.

## Config

File decoding is strict snake_case; durations in files are integer
nanoseconds. Zero durations and counts mean "apply the adapter default".

```yaml
outbox:
  adapter: db
  options:
    dsn: postgres://app:secret@db:5432/app # empty selects sqlite :memory:
    table: outbox # outbox table name
    inbox_table: inbox # inbox table name
    publisher: eventbus # informational: eventbus | queue | ""
    poll_interval: 1000000000 # relay poll cadence; default 1s
    batch_size: 100 # messages claimed per poll
    max_attempts: 5 # publish attempts before DLQ
    retention: 604800000000000 # processed-row retention; default 7d
    lock_seconds: 30 # claim lease while publishing
    dedicated_pool: false # true opens a private pool instead of sharing per DSN
```

CDC variant (postgres logical replication):

```yaml
outbox:
  adapter: cdc
  options:
    dsn: postgres://app:secret@db:5432/app
    prefix: zever_outbox # logical-replication message prefix
    slot: zever_outbox_slot # replication slot
    publication: zever_outbox_pub # pgoutput publication
```

Env (no prefix, `<SERVICE>_<FIELD>`):

```sh
OUTBOX_ADAPTER=db
OUTBOX_DSN=postgres://app:secret@db:5432/app
OUTBOX_POLL_INTERVAL=1000000000
```

`Validate` rejects negative intervals/budgets, table names that are not
safe identifiers, and a `publisher` outside `{eventbus, queue, ""}`. The
cdc adapter additionally requires non-empty `dsn`, `slot`, `publication`,
and `prefix`, and needs `wal_level=logical` on the server. Live cdc
behavior is covered by tests gated behind `POSTGRES_DSN`.

## Resolve via container

```go
import (
    "github.com/zenta-dev/zever/config"
    "github.com/zenta-dev/zever/container"
)

func openStore() error {
    c := container.New(config.Default())
    ob, err := c.Outbox()
    if err != nil {
        return err
    }
    defer ob.Close()
    _ = ob
    return nil
}
```

`Outbox()` resolves lazily and caches the store; on error the cache
clears so the next call retries. Note the container-opened store records
messages but cannot `Start` its relay: core `Options` carry no `Publisher`.
Wire one through the adapter constructor (`adapters/outbox/db`
`OpenFromDB`, `adapters/outbox/cdc` `New`, `adapters/outbox/memory` `New`)
— see the example below.

## Runnable example

One transaction, one event, one idempotent consumer side effect:

```go
package main

import (
    "context"
    "fmt"

    outboxdb "github.com/zenta-dev/zever/adapters/outbox/db"
    "github.com/zenta-dev/zever/config"
    "github.com/zenta-dev/zever/container"
    coredb "github.com/zenta-dev/zever/core/db"
    "github.com/zenta-dev/zever/core/outbox"
)

func main() {
    cfg := config.Default()
    cfg.DB.Path = ":memory:"
    c := container.New(cfg)

    conn, err := c.DB()
    if err != nil {
        panic(err)
    }

    ob, err := outboxdb.OpenFromDB(conn, outboxdb.Options{
        Publisher: outbox.PublisherFunc(func(_ context.Context, msg outbox.Message) error {
            fmt.Println("published", msg.Topic, string(msg.Payload))
            return nil
        }),
    })
    if err != nil {
        panic(err)
    }
    defer ob.Close()

    ctx := context.Background()
    err = coredb.WithTx(ctx, conn, nil, func(ctx context.Context, tx coredb.Tx) error {
        if _, err := tx.Exec(ctx, `CREATE TABLE bookings (id TEXT PRIMARY KEY)`); err != nil {
            return err
        }
        if _, err := tx.Exec(ctx, `INSERT INTO bookings (id) VALUES (?)`, "b-1"); err != nil {
            return err
        }
        return ob.Record(ctx, tx, outbox.Message{
            ID:      "b-1",
            Topic:   "booking.created",
            Payload: []byte(`{"id":"b-1"}`),
        })
    })
    fmt.Println("recorded:", err)

    inbox, ok := ob.(outbox.Inbox)
    if !ok {
        panic("outbox store does not implement outbox.Inbox")
    }
    err = coredb.WithTx(ctx, conn, nil, func(ctx context.Context, tx coredb.Tx) error {
        return inbox.Process(ctx, tx, "b-1", func(ctx context.Context, tx coredb.Tx) error {
            fmt.Println("side effect ran")
            return nil
        })
    })
    fmt.Println("inbox:", err)
}
```

Expected output (the relay is not started here; `Start` publishes stored
messages through the same `Publisher`):

```text
recorded: <nil>
side effect ran
inbox: <nil>
```

How the pieces fit:

- `Record` inserts into the outbox table in the caller's transaction; a nil
  `tx` fails with `ErrTxRequired`. Trace context from `ctx` is injected
  into the stored headers so the consumer continues the originating trace.
- The relay claims a batch with an atomic `UPDATE ... RETURNING` (postgres
  adds `FOR UPDATE SKIP LOCKED`; sqlite serializes on a process-local
  mutex), publishes each message through the `Publisher`, marks successes
  `processed`, and retries failures with `shared/retry` backoff. Messages
  that exhaust `max_attempts` are marked `failed` — the dead-letter queue —
  and left for inspection. Processed rows older than `retention` are
  deleted. `Status()` reports `Pending`/`Processed`/`Failed` counters,
  `LastError`, and `Stalled` when the oldest pending message waits too long.
- `Inbox.Process` records `eventID` in the caller's transaction and runs
  the side effect only when the ID is new (`INSERT ... ON CONFLICT DO
  NOTHING`), so at-least-once delivery still applies side effects exactly
  once.

## Adapters

| Adapter | Package | Notes |
|---|---|---|
| `db` | `adapters/outbox/db` | Default; durable sqlite/postgres polling relay, DLQ, retention; also implements `Inbox` |
| `memory` | `adapters/outbox/memory` | Dev/test; publishes synchronously, keeps nothing |
| `cdc` | `adapters/outbox/cdc` | Postgres logical replication via `pg_logical_emit_message`; needs `wal_level=logical` |

All three serve the same `outbox.Store` interface. The cdc adapter emits
the message inside the caller's transaction, so a rollback drops the
event; the consumer tails the WAL through a replication slot and
acknowledges the LSN only after a successful publish.

## Production notes

- Close semantics: `Store.Close() error` with no context (instant-close
  shape). Container closes only resolved services and joins errors via
  `errors.Join`; panics become `*ClosePanicError`.
- Multi-instance behavior: the `db` relay's `FOR UPDATE SKIP LOCKED` claim
  lets any number of replicas relay the same table without double-publishing;
  the claim lease (`lock_seconds`) covers a crash mid-publish — the row
  returns to pending when the lease expires.
- Pool sharing: the `db` adapter shares one pool per exact DSN with every
  other battery on that DSN (first opener's `max_conns` wins); set
  `dedicated_pool: true` for a private pool under sustained load.
- Redaction: message payloads can carry PII. Never log raw option maps;
  use `config.RedactedServices`. Keep payloads small and reference-backed.
- The `memory` adapter is not durable: a crash between `Record` and the
  publisher's ack loses the event. Dev and tests only.

## Troubleshooting

1. `Start` fails with "publisher is nil": the store was opened through the
  container/registry path, which carries no `Publisher`. Wire one through
  the adapter constructor (`OpenFromDB`/`New`) as in the example.
2. Messages sit `pending` forever: the relay is not running (`Start` never
  called) or `Status().Stalled` is true — check `LastError` for the claim
  or publish error.
3. `failed` rows accumulate: the destination rejects the payload or the
  `Publisher` errors. `max_attempts` (default 5) bounds retries; inspect
  `last_error` on the row, fix the cause, and re-drive the row.
4. Duplicate side effects in consumers: the consumer is not idempotent.
  Give every message a stable `ID` and dedupe through `Inbox.Process` (or
  your own idempotency key) in the same transaction as the side effect.
5. cdc adapter fails to start: the server needs `wal_level=logical`, and
  the publication/slot names must match the configured values. Live tests
  run with `POSTGRES_DSN` set.
