title: 'Tutorial: Build a Booking API'
description: A guided walkthrough of the examples/bookings app — schema, migrate, seed, serve, and hit an endpoint.
---

This tutorial walks through `examples/bookings` in the repository: a short-term
space bookings marketplace ("hosts list spaces, guests book them"). It exists
precisely because a rich domain is the only way to exercise `payment`,
`billing`, `geo`, `media`, `search`, and `vectorstore` together — a bare CRUD
app can't. By the end you'll have a real HTTP API running locally, backed by
a `.zen` schema, sqlite, and every zero-infra adapter `config.Default()`
ships.

All commands below run from `examples/bookings/` in a clone of the repo, so
`zever.yaml` and the local `data/` path resolve correctly.

```sh
cd examples/bookings
```

## 1. The schema

The whole domain — `User`, `Space`, `Booking`, `Review` entities, the
`BookingService` RPCs, two jobs (`SendConfirmation`, `SendReminder`), and a
`Reminder` cron schedule — lives in one file:

```sh
cat schema/bookings.zen
```

You don't need to write this yourself for the tutorial; it's already
checked in. See [Syntax (.zen)](/zever/dsl/syntax-zen/) once you're ready to
extend it.

## 2. Compile and migrate

Generated code (`zenorm`, `proto`, `protogogen`, `gogen`, `openapi`, `atlas`)
is already committed under `generated/` — never hand-edit it, regenerate
with `zever compile` after touching the schema. What you do need to run is
the migration, which creates the local sqlite database:

```sh
zever db migrate --adapter=sqlite --dsn=data/bookings.db schema/bookings.zen
```

## 3. Seed demo data

The seed command is idempotent — safe to run more than once:

```sh
go run ./db/seed
```

This creates a demo host (`host@example.com`), a demo guest
(`guest@example.com`), two spaces, and one confirmed booking.

## 4. Set a JWT secret and serve

The bookings app fails closed if `AUTH_JWT_SECRET` is missing or short —
see [Configuration](/zever/getting-started/configuration/) for why. Export
one (at least 32 bytes, never commit a real one):

```sh
export AUTH_JWT_SECRET=dev-only-secret-at-least-32-bytes-long
go run ./cmd/server
```

The server listens on `:8080` by default (`-addr` flag to change it).

## 5. Start the worker (jobs + scheduler)

In a second terminal, still exporting the same `AUTH_JWT_SECRET`:

```sh
go run ./cmd/worker
```

This registers `SendConfirmation` (queue `default`) and `SendReminder`
(queue `low`) at concurrency 4, and starts the embedded scheduler firing the
`Reminder` cron (`0 9 * * *`). `SendConfirmation` sends a mail receipt via
the `mailer/log` adapter, a guest push via `notification/log`, and delivers
a `booking.created` webhook event to any configured target (skipped
quietly when none is set — see the README's webhook section for the
`BOOKINGS_WEBHOOK_*` environment variables).

## 6. Hit the API

Register a guest and log in:

```sh
curl -s -X POST localhost:8080/api/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"correct horse battery staple"}'

curl -s -X POST localhost:8080/api/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"correct horse battery staple"}'
```

Login returns a JWT. Use it as a bearer token on every other route:

```sh
TOKEN=... # from the login response

curl -s localhost:8080/api/spaces -H "Authorization: Bearer $TOKEN"

curl -s -X POST localhost:8080/api/bookings \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"space_id":"...","start_date":"2026-01-01","end_date":"2026-01-03"}'
```

A successful booking goes through `ratelimit` (allow), `idempotency`
(reserve-or-replay), `lock` (hold the date range), `payment` (stub charge),
and dispatches `SendConfirmation` onto the queue your worker is already
consuming — check its terminal output.

## What you just exercised

One HTTP request touched auth (JWT), rate limiting, idempotency, locking,
payment, the ORM (via `db`), the queue, and — once the worker picks up the
job — mailer, notification, and webhook delivery. That's the point of this
example: a realistic flow is the only way to prove all of those adapters
compose correctly, which is also why `zever doctor --config zever.yaml`
against this app's zero-infra config reports a few expected `FAIL` rows
(missing `ai` API key, missing `geo` fixture data, missing `i18n` embed FS)
— see the app's own `README.md` for the exact list. Those are deliberate
zero-infra gaps in the example, not framework bugs.
