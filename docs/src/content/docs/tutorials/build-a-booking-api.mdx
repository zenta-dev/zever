You will run `examples/bookings`, a space marketplace where hosts list spaces and guests book them. It takes about 15 minutes. You need Go 1.27+, the `zever` CLI, and a repo clone. You end with a real HTTP API on sqlite and the zero-infra adapters.

All commands run from `examples/bookings/` so `zever.yaml` and the relative `data/` path resolve.

```sh
cd examples/bookings
```

## Read the schema

The whole domain lives in one file: the `User`, `Space`, `Booking`, and `Review` entities, the `BookingService` RPCs, two jobs (`SendConfirmation`, `SendReminder`), and a `Reminder` cron schedule.

```sh
cat schema/bookings.zen
```

Checkpoint: you see the entity blocks, the RPC list, and the job and schedule declarations. The file is already checked in. See [Zen syntax](../../reference/zen-syntax/) when you want to extend it.

## Migrate the database

Generated code (`zenorm`, `proto`, `protogogen`, `gogen`, `openapi`, `atlas`) is committed under `generated/`. Never hand-edit it; regenerate with `zever compile`. You only need the migration, which creates the sqlite database:

```sh
zever db migrate --adapter=sqlite --dsn=data/bookings.db schema/bookings.zen
```

Checkpoint:

```text
applied 4 tables to data/bookings.db
```

If you run `zever doctor --config zever.yaml` from another directory, the db check reports a path miss, so run it from here.

## Seed demo data

The seed is idempotent, so you can run it more than once:

```sh
go run ./db/seed
```

Checkpoint:

```text
seeded host host@example.com
seeded guest guest@example.com
seeded 2 spaces
seeded 1 confirmed booking
```

## Set a JWT secret and serve

The app fails closed when `AUTH_JWT_SECRET` is missing or under 32 bytes. See [Configuration](../../guides/operate/configuration/) for why. Export one (never commit a real one):

```sh
export AUTH_JWT_SECRET=dev-only-secret-at-least-32-bytes-long
go run ./cmd/server
```

Checkpoint (`-addr` changes the port):

```text
listening on :8080
```

<Aside type="caution" title="Fail-closed secret">
With a missing or short secret, the process exits at startup with an error naming the field instead of serving insecurely.
</Aside>

## Start the worker

In a second terminal, export the same secret and start the worker (jobs plus scheduler):

```sh
export AUTH_JWT_SECRET=dev-only-secret-at-least-32-bytes-long
go run ./cmd/worker
```

Checkpoint:

```text
registered SendConfirmation (queue default, concurrency 4)
registered SendReminder (queue low, concurrency 4)
scheduler started: Reminder (0 9 * * *)
```

`SendConfirmation` sends a mail receipt (`mailer/log`), a guest push (`notification/log`), and a `booking.created` webhook to any configured target (skipped quietly when none; the app README lists `BOOKINGS_WEBHOOK_*`). `SendReminder` notifies guests of confirmed bookings starting within 7 days.

## Call the API

Register a guest:

```sh
curl -s -X POST localhost:8080/api/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"correct horse battery staple"}'
```

```text
{"id":"01J0000000000000000000000","email":"you@example.com"}
```

Log in. The response holds a JWT to use as a bearer token on every other route:

```sh
curl -s -X POST localhost:8080/api/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"correct horse battery staple"}'
```

```text
{"token":"eyJhbGciOi..."}
```

List spaces, then book one:

```sh
TOKEN=... # from the login response

curl -s localhost:8080/api/spaces -H "Authorization: Bearer $TOKEN"
```

```text
{"spaces":[{"id":"...","title":"..."},{"id":"...","title":"..."}]}
```

```sh
curl -s -X POST localhost:8080/api/bookings \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"space_id":"...","start_date":"2026-01-01","end_date":"2026-01-03"}'
```

```text
{"id":"...","status":"confirmed","payment":"succeeded"}
```

Checkpoint: the worker terminal now shows the mail receipt line, the push line, and either the webhook delivery or the quiet skip. That proves the queue handoff.

## Trace one booking through the stack

A successful booking request passes, in order, through:

1. `auth`: the bearer JWT is verified and the subject is attached to the context.
2. `ratelimit`: the per-guest quota is checked; over quota returns 429 before any state changes.
3. `idempotency`: the request key is reserved, so a retried POST with the same key replays the first result instead of double-booking.
4. `lock`: the space date range is held so concurrent bookings for overlapping dates cannot both confirm.
5. `payment`: a stub charge with `auto_approve` confirms the booking without a provider round trip.
6. `queue`: `SendConfirmation` is dispatched to the worker.

## Understand the doctor failures

```sh
zever doctor --config zever.yaml
```

Expect FAIL rows for `ai` (no API key in zero-infra config), `geo` (missing fixture data), and `i18n` (missing embed FS), plus possibly `db` if you ran it outside `examples/bookings/` and `webhook` (the queue variant needs its queue reference). These are deliberate zero-infra gaps in the example, not framework bugs. The app `README.md` lists them. Do not change framework code to fix them.

## What you built

One HTTP request touched auth, rate limiting, idempotency, locking, payment, the ORM, the queue, and then mailer, notification, and webhook delivery through the worker.

<details>
<summary>Troubleshooting</summary>

**The server exits immediately naming `AUTH_JWT_SECRET`.** The secret is missing or under 32 bytes. Export a longer dev-only value.

**`curl` returns 401 on `/api/spaces`.** The `Authorization: Bearer $TOKEN` header is missing, or the token came from a different secret. Log in again in the terminal where you exported the secret.

**A booking returns 429 or a duplicate.** 429 means the rate limit bit, so wait out the window. A duplicate means you reused an idempotency key; a fresh key creates a fresh booking.
</details>
